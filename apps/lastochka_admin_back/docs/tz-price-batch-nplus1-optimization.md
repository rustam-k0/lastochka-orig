# ТЗ: оптимизация обработки ценовых/остаточных батчей (устранение N+1)

Модуль: `mendev_admin_back`
Компонент: RabbitMQ consumer `product_batches` (очередь `admin_product_batches_in`)
Приоритет: высокий (блокирует первичную раскатку цен по сети, backlog разгребается ~сутки)
Автор диагностики: аналитик, 2026-08-12

## 1. Цель

Сократить время обработки одного ценового батч-сообщения (500 позиций) с текущих ~30 секунд до единиц секунд за счёт устранения N+1: перевести per-item поток запросов на bulk-операции. Целевой ориентир: пропускная способность консьюмера с ~16 позиций/сек до >200 позиций/сек, чтобы полная раскатка сети (тысячи батчей) укладывалась в минуты, а не в сутки.

Метрика приёмки: на dev-стенде обработка одного `price_batch_updated` из 500 позиций (лог `Product batch processed`) занимает не больше 5 секунд по таймстампам логов при неизменном результате в таблицах `prices` (`value`, `price_without_discount`, `price_per_small_unit`, `price_per_kg`, `step`).

## 2. Контекст

### Где живёт
- Хендлер батча: `app/RabbitMQ/Handlers/ProductBatchHandler.php`, методы `processPriceBatch()` (стр. 48), `processStockBatch()` (стр. 140), общий `resolveItems()` (стр. 296).
- Полный per-item путь: `app/Transformers/ProductEventTransformer.php`, метод `processPriceUpdatedEvent()` (стр. 2006), внутри него `processPrice()` (стр. 1038), `processQuantity()` (стр. 1123 для остатков).
- Сервисы, вызываемые на каждую позицию:
  - `App\Services\Quantum\CategoryQuantumService::applyToProduct()` (вызов на стр. 2069 транформера).
  - `App\Services\ProductFillPercentService::recalculate()` (вызов на стр. 2083).

### Триггер
Событие `price_batch_updated` (и `stock_batch_updated`) от `mendev_1c_parser` в очередь `admin_product_batches_in`. Одно сообщение несёт до 500 позиций вида `{id, price, discount_price}` (payload ~42 КБ). Источник событий сейчас `1c`, режим сетевого каталога включён.

### Как вписано в архитектуру
`resolveItems()` уже оптимизирован: metadata и товары подгружаются двумя SELECT на весь батч. Узкое место находится дальше, в per-item обработке. После записи цены admin_back публикует событие вниз по цепочке (storefront обновляет `store_products`), эту публикацию менять не требуется.

## 3. Диагностика (обоснование)

Замеры на dev 2026-08-12:
- Очередь тает ~3 сообщения/мин на тяжёлых ценовых батчах, backlog ~3500 сообщений.
- Лог: на каждый батч `"items_total":500, "processed":500, "unchanged":0`. Быстрый no-op путь `priceUnchanged()` при первичной загрузке не срабатывает (строки `prices` ещё нет), все 500 позиций идут полным путём.
- `strace` рабочего процесса консьюмера: ~1185 обращений к MySQL за 2 секунды, 98% времени процесса в `sendto`/`recvfrom`/`poll` по сокету БД. То есть время уходит в число последовательных запросов, а не в CPU, диск или fsync.
- Проверено, что тюнинг БД не помогает: `sync_binlog=0`, освобождение свопа и `innodb_buffer_pool_size=1GB` пропускную способность не меняют, так как не уменьшают число round-trip'ов. Все правки откачены, стенд в исходном состоянии.

Вывод: на одну позицию приходится порядка 15-30 запросов, на батч 7500-15000, что подтверждает strace (~20 тыс.). Это классический N+1 в коде.

## 4. Источники избыточных запросов (что именно резать)

На одну ценовую позицию сейчас выполняется:

1. **Двойная запись в одну и ту же строку `prices`.**
   `processPrice()` (стр. 1042-1094) открывает транзакцию, делает `Price::lockForUpdate()` + `save()` (записывает `value` из сырой цены). Сразу после `CategoryQuantumService::applyToProduct()` (стр. 2069) открывает вторую транзакцию и повторно перезаписывает ту же строку `prices` пересчитанным квантовым значением. Два `BEGIN`/`SELECT ... FOR UPDATE`/`UPDATE`/`COMMIT` на одну позицию вместо одного.

2. **`$product->fresh()` на стр. 2069.** Полный `SELECT * FROM products WHERE id = ?` для товара, который уже загружен в память в `resolveItems()`. Лишний SELECT на каждую позицию.

3. **Повторный `resolveShopId($shopCode)`.** Вызывается в `processPrice()` (стр. 1040), в `processPriceUpdatedEvent()` для аргумента `applyToProduct()` (стр. 2070) и внутри `applyToProduct()`. Один и тот же `shop_code` для всего батча резолвится в `shops.id` многократно.

4. **`ProductFillPercentService::recalculate()` на каждую позицию (стр. 2083).** Самая тяжёлая часть: пересчёт процента заполненности карточки подгружает атрибуты, изображения, документы товара и сохраняет `products`. При изменении только цены это перечитывание всей карточки на каждую позицию.

5. **Пер-item транзакции.** 500 пар `BEGIN`/`COMMIT` на батч (по факту 1000 с учётом двойной записи).

## 5. Требуемая логика (решение)

Реализовать в `processPriceBatch()` выделенный bulk-путь для массовой обработки, оставив полный per-item путь только для позиций, которым он реально нужен.

### 5.1 Разрешение shop_id и общих данных один раз на батч
Резолвить `shop_id` из `shop_code` один раз в начале `processPriceBatch()` (частично уже есть: `resolveShopIdForDiff()` стр. 236) и прокидывать вниз, не вызывая `resolveShopId()` внутри per-item методов.

### 5.2 Единый расчёт значений цены без двойной записи
Слить логику `processPrice()` и квантового пересчёта `CategoryQuantumService::applyToProduct()` в один расчёт итоговых полей строки `prices` (`value`, `price_without_discount`, `price_per_small_unit`, `price_per_kg`, `step`) в памяти, до записи. Категории квантов, нужные для пересчёта, подгружать одним запросом на весь батч (eager-load по всем `product_id` батча), а не по одному товару через `fresh()`.

Убрать `$product->fresh()`: использовать уже загруженную модель; самоисцеление `base_unit_type_id` (стр. 2039-2046) применять к in-memory модели и учитывать в расчёте, отдельным перечитыванием не нужно.

### 5.3 Bulk-запись цен

**ВАЖНО (проверено на dev 2026-08-12): у `prices` НЕТ UNIQUE-индекса по (product_id, shop_id, type_id), у `remains` НЕТ UNIQUE по (product_id, shop_id).** Есть только обычные (`Non_unique`) индексы `prices_product_shop_type_index` и `remains_product_shop_index`, уникален лишь `PRIMARY(id)`. Поэтому Laravel `upsert()` в наивном виде НЕ подходит: на MySQL `INSERT ... ON DUPLICATE KEY UPDATE` срабатывает только по реальному UNIQUE/PRIMARY ключу, а при его отсутствии `upsert()` всегда делает INSERT и плодит дубли строк цены на каждом батче. Это ровно тот класс дублей, который вручную вычищала миграция дедупликации (раздел 10), повторно вводить его нельзя.

Выбрать один из двух подходов:

- **Подход A (рекомендуется): добавить UNIQUE-индекс** `prices(product_id, shop_id, type_id)` и `remains(product_id, shop_id)` отдельной миграцией-пререквизитом, затем использовать `upsert()`. Плюсы: правильная модель данных, UNIQUE навсегда закрывает класс дубль-строк (его отсутствие и есть латентная причина инцидента дедупликации). Пререквизит: до навешивания индекса убедиться, что дубль-строк нет (`SELECT product_id,shop_id,type_id,COUNT(*) ... HAVING COUNT(*)>1`, на dev сейчас 0), и проверить, что ни один код-путь не рассчитывает на несколько строк на ключ. Миграция должна быть идемпотентной с guard (`Schema::hasIndex`-проверка) по правилам форка.
- **Подход B (без схемы): явные bulk-UPDATE + bulk-INSERT.** Хендлер уже подгружает существующие цены одним запросом на батч (`processPriceBatch()` стр. 57, `keyBy('product_id')`). Использовать это: разделить посчитанные позиции на «строка существует» → пакетный UPDATE (одним `CASE`/`WHEN` на чанк или чанковым апдейтом) и «строки нет» → `Price::insert($newRows)`. Не полагаться на `ON DUPLICATE KEY`.

В обоих случаях писать чанками (например по 500), каждый чанк в одной транзакции. На первичной раскатке конкурентной записи нет (единственный писатель), поэтому per-row `lockForUpdate` избыточен; при необходимости защиты от гонок оставить блокировку на уровне чанка, не строки.

### 5.4 Отложенный пересчёт fill-percent
Не вызывать `ProductFillPercentService::recalculate()` в цикле. Собрать множество затронутых `product_id` и пересчитать процент заполненности одним bulk-проходом после записи цен (один набор запросов на батч вместо 500). Если цена входит в формулу (LASTOCHKI-JAMI-11653), пересчитать только ценовую компоненту без перечитывания атрибутов/изображений, либо вынести пересчёт в отдельную bulk-джобу по списку id.

**Подтверждено (обязательно, не опционально): цена участвует в fill_percent.** `ProductFillPercentService::calculate()` (стр. 38-39) начисляет `weights['price']`, если у товара есть строка цены с `value > 0`. Значит при появлении ПЕРВОЙ цены у товара (кейс первичной раскатки, ровно то, что делает bulk-путь для новых строк) `fill_percent` обязан вырасти. Bulk-путь, пропускающий пересчёт, оставит `fill_percent` заниженным относительно per-item пути. Наивный per-product `recalculate()` после батча делает `fresh()` с 4 связями на товар и съедает большую часть выигрыша, поэтому нужен именно bulk-пересчёт: (1) загрузить затронутые товары с `prices`/`attributes`/`img`/`categories` пакетно, (2) посчитать `fill_percent` в памяти той же формулой, (3) `DB::table('products')` bulk-update по чанкам. Ценовая компонента бинарна (есть положительная цена или нет), но полный процент зависит и от атрибутов, поэтому пересчёт полный, но батчевый. Пока это не сделано, флаг остаётся выключенным.

### 5.5 Сохранить корректность (обязательные инварианты)
- Весовые/квантовые товары: `value` должен оставаться ценой кванта, а не сырой ценой (иначе регресс LASTOCHKI-JAMI-11200). Bulk-расчёт обязан воспроизводить текущую логику `CategoryQuantumService` для таких позиций.
- Событие без `quantity_step` не сбрасывает существующий `step` (стр. 1056-1062).
- Акционная цена (`discount_price`) не затирается пересчётом от базовой (текущая защита `resolveEffectivePrice()`).
- Идемпотентность повторной доставки (`last_event_id`) и защита от lost update по `last_event_timestamp` (`resolveItems()` стр. 339-347) сохраняются, `bumpMetadata()` (стр. 381) вызывается как прежде.
- Аналог для остатков: те же приёмы применить к `processStockBatch()` / `processQuantity()`, с той же оговоркой про отсутствие UNIQUE на `remains(product_id, shop_id)` (подход A или B из раздела 5.3).

## 6. Edge cases и обработка ошибок
- Позиция без `price`: как сейчас, инкремент `errors`, пропуск (стр. 71-74).
- Товар/metadata не приехали (карточка позже цен): `skipped_missing`, пропуск (`resolveItems()` стр. 332-337). Bulk-путь не должен создавать товар.
- Ошибка на отдельной позиции не должна ронять весь чанк: при переходе на bulk продумать частичный откат (валидные позиции записываются, битые уходят в `errors` с логом `logItemError()`), либо повалидировать до формирования bulk-набора.
- Смешанный батч (штучные + весовые/квантовые): штучные идут быстрым bulk-путём, квантовые при необходимости остаются на полном пути. Разделение по наличию квантовой категории у товара и по `quantity_step`/`measurement_unit` в событии.
- **Коллизия product_id внутри батча — НЕ возникает после дедупликации (проверено), но защиту оставить дешёвой строкой.** Матчинг идёт по `external_id` (1C GUID), `uniqueItems()` уже дедупит позиции батча по `id`, а `event_sync_metadata` после консолидации стала 1:1 (16 150 строк = 16 150 distinct `entity_id`): каждый GUID ведёт на свой каноничный `product_id`. Поэтому два разных GUID не сходятся в один `product_id`, дубль-ключа в bulk-наборе нет. На всякий случай (будущие слияния разных GUID на один товар) перед bulk-записью всё же схлопнуть набор по `(product_id, shop_id, type_id)` с «выигрывает последняя по `event_timestamp`» — это дешёвая strtok-защита, а не обязательный по текущим данным шаг.
- **Soft-deleted дубль — подтверждённый механизм (см. раздел 10).** `resolveItems()` грузит товары через `Product::withTrashed()` (стр. 322), и это НЕ случайность: soft-delete карточки сам по себе НЕ отвязывает её от событий, единственная отвязка — перевес `event_sync_metadata.entity_id` на оригинал. После дедупликации дубли помечены `deleted_at`, а metadata перевешана на живые карточки. Bulk-путь обязан: (1) не писать цены/остатки в soft-deleted товар (позиция с trashed-товаром → `skipped_missing`/`errors` с логом), (2) не создавать заново строку цены/остатка для товара, у которого metadata ещё могла указывать на дубль в момент гонки. Guard от записи в trashed особенно важен, потому что `processPrice()` при отсутствии строки СОЗДАЁТ её (стр. 1087-1092) — именно так гонка при миграции пересоздала 39 тыс. цен на дублях.

## 7. Нефункциональные требования
- Атомарность: запись цен на уровне чанка транзакционна, частичный сбой не оставляет строку в промежуточном состоянии.
- Идемпотентность: повторная доставка того же `event_id` не меняет данные (сохранить текущий guard).
- Производительность: цель раздела 1, проверять по таймстампам лога `Product batch processed`.
- Обратная совместимость: формат исходящих событий вниз по цепочке (storefront/purchase/delivery) не меняется.

## 10. Взаимодействие с дедупликацией дублей товаров (контекст 2026-08-12, миграция ЗАВЕРШЕНА)

Разовая миграция слияния дублей каталога выполнена (`dedup_catalog.sh` для `mendev_djami`, `dedup_storefront.sh` для `mendev_store`, логи и бэкапы `/home/server/dedup_catalog.log`, `/home/server/backups/dedup-*`). Служебные таблицы `_dup_map`, `_remains_keep`, `_prices_keep(2)`, `_dup_map_store` оставлены для аудита.

### Итог (проверено на dev)
- Причина дублей: выгрузка 1С от 08.08 шла карточками per-shop, все падали в `shop_id=1`, повтор номенклатуры упирался в UNIQUE(shop_id, articul), счётчик-петля генерила синтетические артикулы `1C-{sku}-{hash8}[-N]`. Итог: 55 491 карточка = 16 152 реальных + 39 339 дублей.
- После миграции: `products` 55 491 всего, `trashed=39 339`, живых 16 152. `event_sync_metadata` (products) стала 1:1: 16 150 строк = 16 150 distinct `entity_id`.

### Ключевые факты, влияющие на ТЗ (учтены в разделах 5.3 и 6)
1. **Коллизии product_id в батче НЕТ.** Ранее ожидалась (первая редакция ТЗ), но подтверждено: metadata теперь 1:1, каждый GUID ведёт на свой каноничный товар, `uniqueItems()` дедупит GUID в батче. Схлопывание набора по ключу оставлено как дешёвая защита на будущее, не как обязательное требование по текущим данным (раздел 6).
2. **Главный технический риск bulk-записи: у `prices`/`remains` НЕТ UNIQUE-индекса** по (product_id, shop_id[, type_id]). Это и есть латентная причина инцидента: `processPrice()` при отсутствии строки её СОЗДАЁТ, поэтому наивный `upsert()` без UNIQUE плодил бы дубли строк. Раздел 5.3 обязывает выбрать подход A (добавить UNIQUE миграцией) или B (явные bulk-UPDATE+INSERT). Подход A заодно закрывает сам класс дубль-строк.
3. **Матчинг через `Product::withTrashed()` намеренный:** soft-delete не отвязывает карточку от событий, отвязка только перевесом `event_sync_metadata.entity_id`. Guard от записи в trashed обязателен (раздел 6).
4. **Грабля рестарта консьюмеров во время миграции.** `supervisorctl stop` не гарантия: CI-деплой любого репо форка делает `supervisorctl restart` и поднимает консьюмеры обратно (в этот раз ~через 3 мин, гонка пересоздала 39 тыс. цен на дублях через ещё-старую metadata; дочищено идемпотентным повторным переносом). Актуально для любого будущего bulk-бэкфилла/миграции по этим таблицам: перед массовыми операциями учитывать, что параллельный деплой оживит консьюмеры. Контроль после: `SELECT COUNT(*) FROM prices pr JOIN _dup_map m ON m.dup_id=pr.product_id` (и то же для remains) должно быть 0.
5. **Порядок работ.** Оптимизацию внедрять и тестировать на пост-дедуп схеме (metadata указывает на каноничные карточки). Тестовые данные держать в слитом состоянии.
6. **Витрина требует парного фикса.** У `mendev_storefront_back` свой консьюмер батчей и трансформер `RabbitMQ/Transformers/ProductEventTransformer.php` (~1806 строк) с тем же per-item N+1 и таблицей масштаба (`store_products` ~5,37 млн строк), и она тоже прошла дедупликацию. Проверить наличие UNIQUE на storefront-аналогах `prices`/`remains` (у store своя схема) и оформить отдельным ТЗ, ссылаясь на этот документ.

## 11. Риски и план внедрения

Оценка перед стартом (проверено на dev 2026-08-12). Ключ `prices(product_id, shop_id, type_id)` под UNIQUE чистый: 0 NULL в колонках ключа, один `type_id`, 0 дубль-групп, 7,41 млн строк; `remains(product_id, shop_id)` тоже без NULL. Стопперов нет, но два риска реально способны навредить.

### 11.1 Блокеры (снять до написания кода)
1. **Мина с тестовой БД.** В `phpunit.xml` строки `DB_CONNECTION=sqlite` / `DB_DATABASE=:memory:` закомментированы, тесты берут БД из активного `.env`. Прогон новых тестов с `RefreshDatabase` против dev/боевого `.env` = `migrate:fresh` = снос рабочей БД. Обязательно: локальная тестовая БД, `DatabaseTransactions` (не `RefreshDatabase`), тесты НИКОГДА не запускать на сервере/в pod/в CI-shell.
2. **Радиус поражения.** Фича правит самый денежный путь (цены по 1478 магазинам), выкатка push в master + `supervisorctl restart all` сразу пускает bulk-путь по всему каталогу. Тонкий баг (например регресс LASTOCHKI-JAMI-11200: `value` весового = сырая цена вместо цены кванта, ×1000) портит цены каталога целиком и быстро. Митигировать: bulk-путь за фича-флагом + shadow-режим (посчитать по-новому, сравнить с текущим на подвыборке, писать по-старому), полное включение после сверки.

### 11.2 Управляемые риски
3. **UNIQUE-индекс (подход A) на 7,41 млн строк.** `ALTER TABLE ADD UNIQUE` на таблице такого размера на свопящейся 2-ядерной dev-машине блокирующий и небыстрый. Делать в спокойное окно, миграцией с guard (`Schema::hasIndex`) и через `DB::table`, не Eloquent (правила форка, иначе CI валится на правах логов).
4. **Сохранить публикацию цен вниз по цепочке.** Есть кастомное событие `product.price_updated` (`config/rabbitmq-events.php:156`) и диспатч `ProductUpdated` в outbox → storefront (`ProductEventTransformer` стр. 939). `processPrice()` пишет через `Price::withoutEvents()`, значит эмиссия НЕ завязана на Eloquent-события Price, но bulk-рефактор обязан сохранить триггер исходящего события на каждый затронутый товар, иначе storefront/purchase/delivery перестанут получать цены. Покрыть отдельным тестом.
5. **Полнота переноса edge-логики.** Bulk-расчёт обязан воспроизвести все накопленные кейсы (самоисцеление единицы, квант, скидка, сохранение `step` без `quantity_step`, раздел 5.5). Снимается TDD против существующих тестов трансформера + новыми регрессами.

### 11.3 Порядок внедрения (рекомендуемый)
1. Разработка локально на изолированной тестовой БД, TDD от существующих тестов трансформера.
2. Bulk-путь реализовать за фича-флагом с shadow-сравнением (по-новому считаем, сверяем с текущим результатом, пишем по-старому).
3. Пререквизит подхода A: миграция UNIQUE-индекса в спокойное окно, с предварительной проверкой отсутствия дубль-строк.
4. Прод/dev-верификация и включение флага ТОЛЬКО после того, как текущий ценовой backlog дойдёт и дедуп-сессия полностью закроется (не смешивать два крупных изменения на одном каталоге).
5. Контроль после включения: тайминги батча из лога (цель раздела 1) + сверка значений `prices` по обеим сторонам (раздел 9) + отсутствие дубль-строк по ключу.
