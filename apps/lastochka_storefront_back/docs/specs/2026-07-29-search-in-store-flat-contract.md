# Поиск товаров: плоская выдача с пагинацией по товарам

Контракт существующего API storefront_back для мобильного приложения Ласточки. Описывает ручку, которая отдаёт результаты поиска одним плоским списком товаров с пагинацией по товарам.

## Что изменилось

Документ фиксирует два факта о текущем сервере:

1. У ручки `GET /api/v1/search/products` параметр `perPage` задаёт количество магазинов на странице, `total` равен числу магазинов, `hasMore` означает наличие следующей страницы магазинов. Количество товаров внутри каждого магазина ограничено параметром `productsPerStore` (по умолчанию 10, максимум 50). Полный список товаров эта ручка не отдаёт по построению: она предназначена для выдачи, сгруппированной по магазинам.
2. Плоский список всех найденных товаров с настоящей пагинацией по товарам отдаёт другая ручка: `GET /api/v1/search/stores/{storeId}/products`. У неё `total` равен общему числу найденных товаров, `hasMore` означает наличие следующей страницы товаров, `perPage` задаёт количество товаров на странице. Поскольку в приложении один магазин, поиск по этому магазину эквивалентен поиску по всему ассортименту.

Плюс одно изменение на сервере:

3. У `GET /api/v1/search/stores/{storeId}/products` появилось поле `categories`: категории, в которых лежат найденные товары, с количеством товаров в каждой. Предназначено для чипов-фильтров над лентой результатов. Изменение обратно совместимо, выпущенные версии приложения новое поле игнорируют.

## База

| | |
|---|---|
| Endpoint | `GET /api/v1/search/stores/{storeId}/products` |
| Dev | `https://store.djami.comrades.dev` |
| Prod | `https://lastochki.store` |
| Auth | Не требуется. Переданный Bearer-токен на результат не влияет: отбор идёт по указанному магазину, без фильтрации по адресу и типу пользователя |
| Content-Type | `application/json` |
| Rate limit | 100 запросов в минуту (общий throttle группы `/search/*`), при превышении HTTP 429 |

`{storeId}`: числовой id магазина. Возвращается ручкой `GET /api/v1/stores` (поле `id`). Справочно: сейчас и на dev, и на prod магазин один, id = 2.

## Ручка

### GET /api/v1/search/stores/{storeId}/products

Query-параметры:

| Поле | Тип | Обяз. | Описание | Ограничения |
|---|---|---|---|---|
| `query` | string | да | Поисковый запрос | 2..255 символов, пробелы по краям обрезаются |
| `page` | int | нет | Номер страницы, по умолчанию 1 | min 1 |
| `perPage` | int | нет | Товаров на странице, по умолчанию 20 | 1..100 |
| `onlyDiscounted` | bool | нет | Только товары со скидкой | |
| `sugarFree` | bool | нет | Только товары без сахара | |
| `brandId` | int | нет | Фильтр по бренду | min 1 |
| `categoryId` | int | нет | Фильтр по категории | min 1 |

Snake_case-алиасы `only_discounted`, `sugar_free`, `brand_id`, `category_id` принимаются как устаревшие и работают идентично camelCase-вариантам.

Форма ответа:

```json
{
  "hasMore": true,
  "data": [ { ...Product... } ],
  "total": 33,
  "categories": [
    { "id": 46089, "name": "Хлеб нашей пекарни", "count": 14 },
    { "id": 46091, "name": "Хлеб, лаваш, лепешки", "count": 8 }
  ]
}
```

| Поле | Тип | Описание |
|---|---|---|
| `data` | Product[] | Товары запрошенной страницы |
| `total` | int | Общее число найденных товаров в магазине по данному запросу и фильтрам |
| `hasMore` | bool | Есть ли следующая страница товаров: `(page * perPage) < total` |
| `categories` | Category[] | Категории, в которых лежат найденные товары. Всегда присутствует, `null` не приходит |

Элемент `categories`:

| Поле | Тип | Описание |
|---|---|---|
| `id` | int | id категории, пригодный для передачи обратно в `categoryId` |
| `name` | string | Название категории |
| `count` | int | Сколько товаров текущей выдачи лежит в этой категории |

## Секция categories

Считается по фактической выдаче: категория попадает в список только если в ней есть хотя бы один найденный товар. Поэтому тап по любому чипу гарантированно вернёт непустой результат, а поле `count` заранее показывает, сколько именно товаров там окажется.

| Свойство | Поведение |
|---|---|
| Охват | Вся найденная выдача, а не текущая страница. Секция приходит одинаковой на каждой странице пагинации, достаточно взять её с первого запроса |
| Порядок | По `count` по убыванию, при равенстве по названию по возрастанию. Порядок стабилен между страницами |
| Размер | Не более 30 элементов, срез после сортировки |
| Влияние `categoryId` | Не влияет. Секция считается так, будто `categoryId` не передавали, поэтому после тапа по чипу список чипов остаётся полным и можно переключиться на соседнюю категорию, не снимая фильтр |
| Влияние остальных фильтров | `query`, `brandId`, `onlyDiscounted`, `sugarFree` учитываются: секция описывает ту же выдачу, что и `data` |
| Наличие товара | Товар, которого по факту нет на остатке, свою категорию в секцию не тянет: учитываются те же товары, по которым считается `total` |
| Отключённые категории | Категория, выключенная целиком или выключенная в этом магазине, в секцию не попадает, даже если её товары нашлись |

Категории могут быть как конечными, так и промежуточными: критерий не глубина в дереве, а наличие товаров, привязанных к категории напрямую. Корневые категории без собственных товаров в секцию не попадают.

## Типы

Элемент `data` тот же объект Product, что и элементы `data[].products` в `GET /api/v1/search/products`. Форма не менялась. Поля: `id`, `sku`, `title`, `description` (может быть null), `price`, `priceOld` (может быть null), `discountPercent` (может быть null), `currency`, `images[]` (`id`, `path`), `isFavorite`, `servedWarm`, `composition` (может быть null), `additionalInfo` (может быть null), `proteins`, `fats`, `carbohydrates`, `calories` (каждое может быть null), `weight` (может быть null), `attributes[]`, `rating` (может быть null), `reviewsCount`, `supplements[]`, `hasSupplements`, `hasRequiredSupplements`, `quantityStep`, `measurementUnit`, `measurementUnitLabel`, `stockQuantity`, `availableFrom` (может быть null), `isConfigurable`, `customCheckboxes`.

`isFavorite` без авторизации всегда `false` (Bearer этой ручкой не учитывается).

## Поведение сервера

| Условие | Что отдаёт сервер |
|---|---|
| Порядок выдачи | Релевантность Meilisearch: количество совпавших слов запроса, затем меньше опечаток, затем близость слов, затем поле совпадения (название выше артикула; поиск идёт по `title` и `sku`), затем точность совпадения. Сортировки по популярности или продажам нет |
| Опечатки | Допускается 1 опечатка в словах от 4 букв, 2 опечатки от 8 букв. Последнее слово запроса матчится и по префиксу, поэтому запрос «булочк» находит и «Булочка», и «Булочки» |
| Видимость товаров | В выдачу попадают только активные товары с ценой больше 0 и с наличием на остатке; остаток дополнительно перепроверяется по базе, поэтому `total` всегда совпадает с реально доступными товарами |
| Meilisearch недоступен | HTTP 200 с пустой выдачей: `{"hasMore": false, "data": [], "total": 0, "categories": []}` |
| Пустой результат поиска | HTTP 200, `data: []`, `total: 0`, `hasMore: false`, `categories: []` |

## Коды ответов

| Ситуация | HTTP | Тело |
|---|---|---|
| Успех (включая пустую выдачу) | 200 | `{hasMore, data, total, categories}` |
| Магазин с таким id не существует | 404 | `{"message": "..."}` |
| Ошибка валидации: `query` отсутствует, короче 2 символов, `perPage` больше 100 и т.п. | 422 | Стандартный Laravel-формат: `{"message": "...", "errors": {"query": ["..."]}}` |
| Больше 100 запросов в минуту | 429 | `{"message": "Too Many Attempts."}`, заголовок `Retry-After` |

## Обратная совместимость

Добавление `categories` в `GET /api/v1/search/stores/{storeId}/products` обратно совместимо: остальные поля не менялись, выпущенные версии приложения новое поле игнорируют.

`GET /search/products` и `GET /search/suggestions` работают как раньше. У `GET /search/products` семантика `perPage`, `total`, `hasMore` остаётся магазинной (контракт используется приложением Аладдина в мультимагазинном сценарии и меняться не будет), и его секция `categories` сохраняет прежнюю семантику поиска по названию, а не по товарам.
