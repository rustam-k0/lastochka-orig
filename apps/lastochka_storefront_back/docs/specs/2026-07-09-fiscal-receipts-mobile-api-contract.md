# Фискальные чеки (54-ФЗ) в приложении (LASTOCHKI-JAMI-11651)

Контракт API для клиентского приложения. Описывает, что отдаёт бэкенд по фискальным чекам заказа и как приходит пуш «Чек готов». Чек формируется по 54-ФЗ (онлайн-оплата и оплата наличными при получении) через выбранный в админке фискализатор (АТОЛ Онлайн или ЮKassa). Для клиента источник чека прозрачен — формат ответа одинаков для обоих.

## Что изменилось

1. В ответе `GET /api/v1/orders/{order}/receipts` появилось поле `receiptUrl` — прямая ссылка на чек в ОФД (заполнено, когда чек пробит через АТОЛ; `null`, когда через ЮKassa).
2. Поле `seller` теперь берётся из настроек активного фискализатора (реквизиты продавца), формат прежний `{name, inn}`.
3. Эндпоинт теперь возвращает чеки и для оплаты наличными (ранее — только для онлайн-оплаты), и для чеков, пробитых через АТОЛ. Формат позиций (`items`) единый для всех провайдеров.
4. Добавлен пуш-нотификейшн «Чек готов» (FCM) — приходит один раз в момент, когда фискальный чек по заказу успешно зарегистрирован.

## База

| | |
|---|---|
| Endpoint | `GET /api/v1/orders/{order}/receipts` |
| Dev | `https://store.djami.comrades.dev` |
| Prod | (уточняется у бэкенда) |

| Rate limit | Нет отдельного throttle на этой ручке |

## Ручки

### `GET /api/v1/orders/{order}/receipts` — список фискальных чеков заказа

Путь: `order` — числовой id заказа.

Тело запроса: нет. Аргументов нет.

Ответ `200`: объект с ключом `data` — массив чеков (0..N). У заказа может быть чек прихода (`payment`) и, при возврате, чек возврата (`refund`). Массив пуст, если по заказу ещё нет ни одного чека.

При обращении сервер лениво досинхронизирует статус ещё не завершённых чеков, поэтому свежезарегистрированный чек виден в том же ответе.

```json
{
  "data": [ { /* Receipt */ } ]
}
```

## Типы

### Receipt

```
Receipt {
  type: string            # "payment" (приход) | "refund" (возврат прихода)
  status: string          # "pending" (регистрируется) | "succeeded" (пробит) | "canceled" (не пробит/ошибка)
  registered_at: string   # ISO 8601, момент фискализации; может быть null пока status != "succeeded"
  total: string           # сумма чека, "0.00"
  items: ReceiptItem[]    # позиции чека (единый формат для АТОЛ и ЮKassa)
  vat: VatSummary[]       # свод НДС по ставкам
  fiscal: Fiscal | null   # фискальные реквизиты; null пока чек не пробит (status != "succeeded")
  receiptUrl: string | null  # ссылка на чек в ОФД (заполнено для АТОЛ; null для ЮKassa)
  qr: string | null       # строка для QR-кода чека по 54-ФЗ; null пока чек не пробит
  seller: Seller          # реквизиты продавца
}
```

### ReceiptItem

```
ReceiptItem {
  description: string     # наименование позиции
  quantity: string        # количество в фискальном чеке, "1.00"
  amount: string          # цена за единицу в фискальном чеке, "689.00" (НДС включён в цену)
  vat_code: number        # код ставки НДС ЮKassa: 1 без НДС, 2 — 0%, 3 — 10%, 4 — 20%, 5 — 10/110, 6 — 20/120
  vat_rate: string        # ставка в процентах, "20" | "10" | "0"
  vat_amount: string      # сумма НДС в позиции (включённого в цену), "100.00"
}
```

Инвариант позиции чека: `amount × quantity` = сумма позиции (требование 54-ФЗ, строго до копейки). Позиции — **фискальное представление**, а не копия корзины заказа: для весовых/дробных товаров (развес), где цена за единицу с двумя знаками не даёт точную сумму, позиция нормализуется — `quantity = "1.00"`, `amount` = полная сумма позиции. Поэтому `quantity`/`amount` в фискальном чеке могут отличаться от количества/цены той же позиции в заказе. Для отображения чека достаточно `description` + сумма позиции (`amount × quantity`); сопоставлять `quantity` с количеством товара в корзине не следует.

### VatSummary

```
VatSummary {
  vat_code: number        # код ставки (см. выше)
  rate: string            # ставка в процентах, "20"
  amount: string          # суммарный НДС по этой ставке в чеке, "100.00"
}
```

### Fiscal (реквизиты пробитого чека, null пока не пробит)

```
Fiscal {
  fn: string              # номер фискального накопителя (ФН)
  fd: string              # номер фискального документа (ФД)
  fp: string              # фискальный признак (ФП)
}
```

### Seller

```
Seller {
  name: string | null     # наименование продавца из настроек фискализатора
  inn: string | null      # ИНН продавца
}
```

## Поведение сервера

| Условие | Что отдаёт сервер |
|---|---|
| По заказу ещё нет чеков | `data: []` |
| Чек в процессе регистрации | `status: "pending"`, `fiscal: null`, `qr: null`, `registered_at: null` |
| Чек успешно пробит | `status: "succeeded"`, заполнены `fiscal`, `qr`, `registered_at` |
| Ошибка/отказ фискализации | `status: "canceled"`, `fiscal: null`, `qr: null` |
| Чек пробит через АТОЛ | `receiptUrl` — ссылка на чек в ОФД |
| Чек пробит через ЮKassa | `receiptUrl: null` (чек отображается по `qr`/`fiscal`) |
| Онлайн-оплата картой | чек прихода `type: "payment"` появляется после успешной оплаты |
| Оплата наличными при получении | чек прихода `type: "payment"` появляется после доставки заказа |
| Возврат | отдельный чек `type: "refund"` |

Поле `qr` — готовая строка формата 54-ФЗ (`t=<ГГГГММДДTЧЧММ>&s=<сумма>&fn=<ФН>&i=<ФД>&fp=<ФП>&n=<1|2>`), пригодная для рендера в QR-код. `null`, пока чек не пробит.

## Коды ответов

| Ситуация | HTTP | Тело |
|---|---|---|
| Успех | `200` | `{ "data": [ Receipt, ... ] }` |
| Токен отсутствует/просрочен | `401` | `{ "message": "Unauthenticated." }` |
| Заказ не принадлежит пользователю | `403` | `{ "message": "This action is unauthorized." }` |
| Заказ не найден | `404` | `{ "message": "..." }` |

## Пуш «Чек готов» (FCM)

Приходит один раз, когда фискальный чек по заказу переходит в `succeeded`.

```
notification: {
  title: "Чек готов",
  body:  "Фискальный чек по заказу №<order_id> готов"
}
data: {
  type: "receipt_ready",
  order_id: "<id заказа, строка>",
  action: "open_order_details",
  notification_id: "<id in-app уведомления, строка>"
}
```

Все значения в `data` — строки (требование FCM). По `type: "receipt_ready"` и `order_id` определяется, что открыть детали заказа, где чек доступен через `GET /api/v1/orders/{order}/receipts`.

## Обратная совместимость

- Эндпоинт `GET /api/v1/orders/{order}/receipts` и формат `Receipt` не менялись структурно — добавлено только поле `receiptUrl` (новое, может быть `null`). Существующий клиент, читающий `fiscal`/`qr`/`items`/`seller`, продолжает работать.
- Формат позиций `items` (`description`/`quantity`/`amount`/`vat_code` + `vat_rate`/`vat_amount`) единый для всех провайдеров и совпадает с тем, что отдавалось для онлайн-чеков ЮKassa ранее.
- Пуш «Чек готов» — новый тип уведомления (`data.type = "receipt_ready"`); клиент, не знающий этот тип, его игнорирует без последствий.
