# 28. Расширенный поиск с категориями и карточками товаров (METRO-style)

Дата: 2026-07-22. Статус на 2026-07-29 (сверено с кодом): секция категорий реализована (MID-171),
секция карточек товаров `productCards` **не реализована** — в `SearchSuggestionsRequest` нет
параметра `productLimit`, в `SearchService::getSuggestions()` нет такой секции.
Референс UX: metro-cc.ru — при вводе запроса дропдаун показывает три секции: текстовые подсказки, «Категории», «Товары» (карточки с ценой и кнопкой «В корзину») + ссылку «Смотреть все результаты».

## 1. Цель

Выпадающая панель поиска на веб-сайте магазина, которая по мере ввода запроса показывает:
1. текстовые подсказки (автодополнение),
2. секцию «Категории» — кликабельные категории, релевантные запросу, с переходом в каталог категории,
3. секцию «Товары» — до 6 карточек товара (фото, название, цена, старая цена, кнопка «В корзину»),
4. ссылку «Смотреть все результаты» — переход на полную страницу выдачи.

Измеримый результат: один запрос `GET /api/v1/search/suggestions?structured=true` отдаёт все данные для панели; сайт рендерит секции без дополнительных запросов.

## 2. Контекст

- **Бэкенд:** `mendev_storefront_back` (Laravel 12, REST `/api/v1/*`, Meilisearch v1.6).
- **Фронтенд:** веб-сайт магазина — внешний клиент (та же команда, что и мобильное приложение; исходников в наших репозиториях нет). Наша зона — API-контракт + спека для клиентской команды.
- **Триггер:** ввод текста в поисковую строку сайта (debounce ~300 мс, от 2 символов — ограничение UI; API принимает запрос от 1 символа).

### Что УЖЕ реализовано (сверено с кодом 2026-07-29)

- `GET /api/v1/search/suggestions?structured=true` возвращает `{categories, brands, products}`
  (`SearchService::getSuggestions()`):
  - `categories` — формат элемента `{id, name, slug}` (`slug` добавлен 2026-08-26 для перехода
    в каталог по категории). Порядок наполнения: сначала категории, чьё
    название матчится со **всеми** словами запроса (METRO-семантика, MID-171; сравнение
    регистронезависимое через `mb_stripos`, сначала совпадения с начала названия, затем по
    алфавиту), затем добивка активными категориями найденных товаров (поле `category_ids`
    документов Meilisearch); дедуп по id, суммарно не более `limit`. Категории берутся только
    активные и привязанные активной связью (`category_store.is_active = true`) к доступным
    магазинам;
  - `brands` — `{id, title, logoImage}`, где `logoImage` — объект `{url}` с полным URL логотипа
    либо **null**, если логотип не задан. Отбираются активные бренды найденных товаров;
  - `products` — **только строки-названия** (текстовые подсказки), НЕ карточки;
  - параметры: `query` (обязателен, 1–255 символов), `limit` (1–20, default 10),
    `structured` (`0|1|true|false`, default false).
- Meilisearch-документ товара содержит `category_ids`, `price`, `price_old`, `in_stock`,
  `quantity`, `store_id`, `brand_id`, `sku`, `title`, `description`, `rating`, `has_discount`,
  `sugar_free`, `is_active`, `is_configurable`, `is_culinary`, `updated_at` — переиндексация для
  карточек не требуется. (Фильтруемых атрибутов меньше, чем полей документа; `price_old`
  фильтровать нельзя, но в хите он приходит.)
- `GET /api/v1/search/products` принимает `categoryId` (и устаревший алиас `category_id`) —
  переход «клик по категории → выдача внутри категории» поддержан бэкендом.
- Секция `categories: CategoryResource[]` есть и в `GET /api/v1/search/products`
  (параметр `categoriesLimit`, default 5, при значении больше 20 усекается до 20, `0` отключает
  секцию); секция не пагинируется и заполняется даже при нуле найденных товаров и при
  недоступном Meilisearch — см. `docs/api_search.md`.
- Фильтрация подсказок по доступным магазинам адреса (`AvailableStoreService`) встроена в
  suggestions: с Bearer-токеном и активным адресом — магазины адреса, иначе — активные магазины
  с учётом типа B2B/B2C. Если доступных магазинов нет, секции пустые.
- `GET /api/v1/search/recommendations` (для пустого состояния и zero-results) существует:
  параметр `limit` (1–50, default 20), ответ `{data: ProductResource[], total: int}`.

### Дельта (что нужно доделать)

Единственный содержательный gap бэкенда: секция карточек товаров в structured-ответе suggestions.

## 3. Данные

### API-контракт (расширение существующего эндпоинта, обратная совместимость обязательна)

`GET /api/v1/search/suggestions?query=молок&structured=true&limit=10&productLimit=6`

Ответ (новое поле `productCards`, существующие секции не меняются):

- `products: string[]` — как сейчас, текстовые подсказки (совместимость с мобильным приложением);
- `categories: [{id, name}]` — как сейчас;
- `brands: [{id, title, logoImage: {url} | null}]` — как сейчас;
- **`productCards`** (новая секция): массив до `productLimit` (default 6, max 10) элементов:
  `{id, title, price, priceOld, unit, quantityStep, image: {url} | null, storeId, inStock, hasDiscount}` — подмножество существующего `ProductResource` (использовать компактный ресурс, не тянуть supplements/promotions/атрибуты).

  Имена полей карточки заданы этим ТЗ и не совпадают с текущим `ProductResource`: там
  `measurementUnit` вместо `unit`, `images: [{id, path}]` вместо `image: {url}`, `stockQuantity`
  вместо `inStock`, а `storeId` и `hasDiscount` в `ProductResource` не отдаются вовсе. Поэтому
  секция собирается отдельным компактным Resource, а не переиспользованием `ProductResource`.

Источник карточек: те же хиты Meilisearch, что уже получены внутри `getSuggestions()` (дополнительный запрос к Meili не нужен) + догрузка моделей из БД по образцу `loadProducts()` (валидация остатка по БД, порядок из Meili, eager `images`).

### Сущности

Новых таблиц/миграций нет. Затрагиваются только `SearchService`, `SearchController`, `SearchSuggestionsRequest`, новый компактный Resource.

## 4. Логика

Happy path:
1. Клиент шлёт `suggestions?structured=true&productLimit=6`.
2. Сервис выполняет текущий Meili-запрос (лимит `limit*3` уже с запасом), собирает titles/categories/brands как сейчас.
3. Из первых N валидных хитов (проверка по БД: active, inStock с учётом `stock_mode=ignore` и `stores.ignore_stock`, hasPrice — тот же фильтр, что в `validProductIds()`) собирает `productCards`.
4. Ответ отдаётся одним JSON.

Edge cases:
- Товар есть в Meili, но пропал из БД / ушёл в 0 остаток → карточка не попадает в выдачу (валидация по БД, приоритет БД над индексом — существующее правило сервиса);
- текущая валидация suggestions: `query` короче 1 символа или отсутствует → 422; `limit` вне 1–20 → 422; `structured` вне `0|1|true|false` → 422. Минимум в 2 символа действует у `/search/products` и `/search/stores/{store}/products`, у suggestions — 1 символ;
- `structured=false` или параметр отсутствует → поведение байт-в-байт как сейчас (плоский `string[]`), мобильное приложение не затронуто;
- пустая выдача → все секции пустые массивы, HTTP 200.

Error handling: сохраняется текущий graceful degradation — при падении Meilisearch лог + пустые секции (плоский `[]` либо объект с тремя пустыми секциями), не 500.

## 5. UI/UX (сторона команды сайта)

Компонент дропдауна под поисковой строкой:
- секции в порядке: текстовые подсказки → «Категории» → «Товары» → «Смотреть все результаты»;
- состояния: loading (скелетоны), empty («ничего не найдено» + рекомендации из `GET /search/recommendations`), error (тихо скрыть панель), success;
- debounce 300 мс, отмена устаревших запросов (race при быстром вводе);
- клик по категории → страница каталога с `categoryId` (выдача через `search/products?query=...&categoryId=...` либо стандартный каталог категории — на выбор команды сайта);
- клик по подсказке → подстановка в строку + полная выдача; клик «Смотреть все» → страница результатов (`search/products`);
- кнопка «В корзину» на карточке → существующий `POST /api/v1/cart` (карточка содержит `storeId` и `quantityStep`);
- клавиатурная навигация (стрелки/Enter/Esc) и закрытие по клику вне панели;
- адаптив: на мобильной вёрстке секции в один столбец.

## 6. Интеграции

Только Meilisearch (существующая). Внешних систем нет.

## 7. Нефункциональные требования

- Rate limit остаётся `throttle:100,1` (на всю группу `search/*`).
- Время ответа suggestions — сопоставимо с текущим (один Meili-запрос + один SELECT по id; целевой p95 < 200 мс).
- Кеширование: сейчас `/search/suggestions` не кешируется вовсе; кешируется только
  `/search/products` — TTL `MEILISEARCH_CACHE_TTL` (по умолчанию 30 сек), причём его ключ
  включает признак B2B, но не адрес и не id пользователя. Допустимо добавить короткий кеш
  подсказок (30 сек), ключ включает query+limit+productLimit+адрес/тип пользователя.
- Обратная совместимость мобильного приложения: плоский режим и существующие структурированные секции не меняются.

## 8. Ожидаемый результат

**Backend (наша сторона):**
- расширение `SearchService::getSuggestions()` секцией `productCards`;
- компактный API Resource карточки; изменения в `SearchSuggestionsRequest` (`productLimit`);
- Feature-тесты: structured c карточками, совместимость плоского режима, фильтрация по остатку/адресу, деградация при недоступном Meili;
- обновление Scramble-аннотаций (OpenAPI) и спеки для клиентской команды (этот файл — контракт);
- деплой: обычный push в master (автодеплой), переиндексация НЕ нужна, `route:clear` по стандартному чек-листу.

**Frontend (команда сайта, вне наших репозиториев):**
- компонент дропдауна по разделу 5, интеграция с `suggestions`, `search/products`, `cart`.

## Оценка трудоёмкости (человеко-дни, для планирования)

| Блок | Работа | Оценка |
|---|---|---|
| Backend API | `productCards` в suggestions + Resource + тесты + OpenAPI | 1–1.5 дня |
| Backend деплой/проверка | деплой, живая верификация на dev | 0.5 дня |
| Frontend сайта | компонент панели: секции, debounce, состояния, переходы, «В корзину» | 2–4 дня (зависит от стека сайта) |
| Интеграция/QA | стыковка, кросс-браузер, мобильная вёрстка | 0.5–1 день |

Итого: **бэкенд ~2 дня**, **фронтенд сайта 2.5–5 дней**; под ключ с интеграцией — примерно **одна рабочая неделя** календарно при параллельной работе сторон. Если команда сайта готова начать с существующего API (категории уже отдаются), фронт может стартовать не дожидаясь бэкенд-доработки — блокировка только по секции карточек товаров.
