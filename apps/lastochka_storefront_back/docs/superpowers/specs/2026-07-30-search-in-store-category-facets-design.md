# Фасеты категорий в поиске по магазину

`GET /api/v1/search/stores/{storeId}/products` дополнительно возвращает секцию `categories`: категории, в которых лежат найденные товары, с количеством. Секция нужна мобильному приложению как ряд чипов-фильтров над лентой результатов; тап по чипу повторяет запрос с `categoryId`.

## Проблема

Ручка отдаёт только `{hasMore, data, total}`. Секция `categories` есть у соседней `GET /api/v1/search/products`, но приложение её не использует: она мультимагазинная и режет товары по `productsPerStore`.

Копировать семантику соседней ручки нельзя. Там категории ищутся по названию подстрокой (`SearchService::searchCategories()`, METRO-семантика), а товары ищутся Meilisearch с опечатками. Из-за расхождения движков запрос `конфета` даёт 204 товара и `categories: []`, а `конфет` даёт четыре категории. При расчёте по фактической выдаче такое расхождение невозможно по построению.

## Контракт

Поле добавляется четвёртым, остальные три не меняются. Изменение обратно совместимо: выпущенные версии приложения игнорируют незнакомое поле.

```json
{
  "hasMore": false,
  "data": [ /* ProductResource, как сейчас */ ],
  "total": 12,
  "categories": [
    { "id": 46089, "name": "Хлеб нашей пекарни", "count": 14 },
    { "id": 46091, "name": "Хлеб, лаваш, лепешки", "count": 8 }
  ]
}
```

| Поле | Тип | Описание |
|---|---|---|
| `categories[].id` | int | id категории, пригодный для передачи в `categoryId` |
| `categories[].name` | string | Название категории |
| `categories[].count` | int | Сколько товаров текущей выдачи лежит в этой категории |

Свойства секции:

- Считается по всей найденной выдаче, а не по текущей странице, и приходит одинаковой на каждой странице пагинации.
- Сортировка по `count` desc, при равенстве по названию по возрастанию. Порядок чипов стабилен между страницами.
- Не более 30 элементов (`config('meilisearch.search.store_categories_limit')`), срез после сортировки.
- Пустая выдача или недоступный Meilisearch дают `[]`. Поле присутствует всегда, `null` не возвращается.

## Расчёт

Источник данных: поле `category_ids` в Meili-документе товара (`SearchService::productToDocument()`), уже индексируется и уже объявлено фильтруемым.

1. Взять хиты Meili, прошедшие валидацию по реальному остатку из БД (`validProductIds()`), то есть ровно тот набор, по которому считается `total`. Товар не в наличии не тянет свою категорию в чипы.
2. Просуммировать вхождения по `category_ids` хитов, получив `count` на категорию.
3. Догрузить `Category::whereIn('id', ...)->active()` с проверкой привязки к запрошенному магазину (`category_store.is_active = 1`). Категория, отключённая в магазине, чипом не становится.
4. Отсортировать, срезать по лимиту, отдать `{id, name, count}`.

### Почему не фильтруем по листовости

Требование «в секции только категории, по которым `categoryId` реально фильтрует» выполняется автоматически. Категория попадает в секцию только если хотя бы один найденный товар привязан к ней напрямую, а `categoryId` транслируется в Meili-фильтр `category_ids = N`, который матчит ровно прямые привязки. Значит тап по любому чипу вернёт минимум те товары, из-за которых чип появился. Пустых чипов не бывает по построению.

Явный фильтр «только листовые» был бы ошибкой. На dev 374 привязки товаров ведут напрямую к категориям, у которых есть дети:

| id | Категория | Детей | Прямых товаров |
|---|---|---|---|
| 46087 | Хлеб и булочки | 6 | 0 |
| 46081 | Горячие блюда | 1 | 72 |
| 46028 | Куханная утварь | 1 | 233 |

46087 давала пустой экран после тапа в старой name-match секции и в фасетную не попадёт никогда, потому что прямых привязок у неё нет. А 46081 и 46028 тоже нелистовые, но `categoryId` по ним возвращает 72 и 233 товара: отсечение по листовости выкинуло бы рабочие чипы.

### Взаимодействие с `categoryId`

Секция считается так, будто `categoryId` не передан. Иначе после первого же тапа лента чипов схлопывается в один элемент и переключиться на соседнюю категорию нельзя, только снять фильтр. Остальные фильтры (`query`, `brandId`, `onlyDiscounted`, `sugarFree`) в расчёте секции участвуют.

Реализация: когда `categoryId` не передан (штатный случай), секция считается из тех же хитов, что и товарная выдача, дополнительных запросов нет. Когда `categoryId` передан, товарная выдача считается как сейчас, а для секции выполняется второй запрос в Meili с теми же фильтрами минус `categoryId` и с `attributesToRetrieve: ['id', 'category_ids']`. Товарная выдача при этом не затрагивается вообще, а лишний запрос платится только когда чип реально нажат.

## Изменения в коде

| Файл | Изменение |
|---|---|
| `config/meilisearch.php` | Ключ `search.store_categories_limit` со значением 30 |
| `app/Services/Search/SearchService.php` | `searchInStore()` возвращает `categories`; приватный хелпер сборки фасетов |
| `app/Http/Controllers/Api/V1/SearchController.php` | `productsInStore()` кладёт `categories` в ответ; докблок Scramble |
| `docs/specs/2026-07-29-search-in-store-flat-contract.md` | Описание нового поля в контракте для мобильного разработчика |

Отдельный API Resource не заводится: три скалярных поля собираются в сервисе.

## Тесты

`tests/Feature/Api/V1/Search/SearchProductsInStoreTest.php`:

- категории найденных товаров приходят с корректным `count`, дедуплицированы, отсортированы по `count` desc;
- категория товара из другого магазина в секцию не попадает;
- неактивная категория и категория с `category_store.is_active = 0` не попадают;
- товар не в наличии не тянет свою категорию в секцию;
- при `categoryId=N` секция остаётся полной, а `data` и `total` сужаются;
- секция одинакова на первой и второй странице пагинации;
- при пустой выдаче приходит `[]`.

## Вне объёма

Расхождение `конфета` против `конфет` в секции `categories` ручки `GET /api/v1/search/products` остаётся: там своя name-match семантика, приложение эту ручку не использует.
