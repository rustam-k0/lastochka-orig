# API оплаты для мобильной разработки

**Base URL:** `https://store.raz-dev.mendev.ru/api/v1` (DNS storefront-домена в процессе настройки)
**Auth:** `Authorization: Bearer {token}` (Sanctum)
**Scramble Docs:** `https://store.raz-dev.mendev.ru/docs/api`

Документ описывает поведение сервера: платёжные ручки, форму ответов и правила
списания. Полный контракт с схемами таблиц и вебхуков: [`docs/specs/08_payments.md`](specs/08_payments.md).

---

## Флоу оплаты

```
1. Первая оплата (новая карта):
   POST /orders с paymentType=card, без paymentCardId
   → заказ создаётся, затем сервер создаёт холд с редиректом
   → в ответе confirmationUrl (страница оплаты ЮKassa)
   → после успешной оплаты ЮKassa шлёт вебхук, карта сохраняется автоматически

2. Оплата сохранённой картой (pre-authorization):
   POST /orders с paymentType=card + paymentCardId=1
   → холд по сохранённой карте выполняется ДО создания заказа
   → отказ банка: заказ не создаётся, ответ 422 payment_declined + reason
   → успех: заказ создан, confirmationUrl = null

3. Списание при завершении сборки:
   grand_total <= холда → capture на фактическую сумму, разница разблокируется
   grand_total  > холда → доплата разницы по сохранённой карте, затем capture холда
```

## Эндпоинты

### POST /orders: создать заказ (платёжная часть)

Полный контракт создания заказа: [`docs/specs/06_orders.md`](specs/06_orders.md).

**Платёжные поля запроса:**

```json
{
  "storeId": 1,
  "addressId": 5,
  "deliverySlotId": 1775109600,
  "idempotencyKey": "uuid",
  "paymentType": "card",
  "paymentCardId": 1
}
```

| Поле | Правила | Описание |
|---|---|---|
| `paymentType` | `sometimes`, `in:cash,card` | Тип оплаты. При отсутствии поля заказ создаётся с `cash` |
| `paymentMethod` | алиас (новое) | Если передан `paymentMethod` и не передан `paymentType`, значение копируется в `paymentType` |
| `paymentCardId` | `nullable`, `integer`, карта принадлежит текущему пользователю | ID сохранённой карты. Несуществующая или чужая карта: `422` с ошибкой валидации |

**Ответ (201):**

```json
{
  "orderId": 148,
  "confirmationUrl": "https://yoomoney.ru/checkout/..."
}
```

`confirmationUrl` может быть null.

**Правила `confirmationUrl`:**

| Условие | confirmationUrl |
|---|---|
| `paymentType: "cash"` | `null`, холд не создаётся |
| `paymentType: "card"` без `paymentCardId` | URL страницы оплаты ЮKassa (холд создаётся после записи заказа в БД) |
| `paymentType: "card"` с `paymentCardId` | `null`: холд по сохранённой карте уже выполнен до создания заказа |
| `paymentType: "card"` с `paymentCardId`, у карты пустой `payment_method_id` | URL страницы оплаты (сервер откатывается на обычный холд с редиректом) |
| Повтор с уже использованным `idempotencyKey` | `null`, в `orderId` возвращается ранее созданный заказ |

**Отказ банка при оплате сохранённой картой (422):**

```json
{
  "error": "payment_declined",
  "reason": "insufficient_funds",
  "message": "Недостаточно средств на карте"
}
```

`reason` (новое) может быть null, если ЮKassa не прислала причину. Заказ при таком
ответе в базу не записывается, товары не резервируются.

Соответствие кодов и сообщений (`PaymentDeclineReason`):

| reason | message |
|---|---|
| `insufficient_funds` | Недостаточно средств на карте |
| `card_expired` | Срок действия карты истёк |
| `invalid_card_number` | Неверный номер карты |
| `call_issuer`, `general_decline` | Платёж отклонён банком |
| `payment_method_restricted` | Операции по карте ограничены банком |
| `fraud_suspected` | Платёж отклонён: подозрение в мошенничестве |
| другое значение или null | Платёж отклонён |

Сумма холда по сохранённой карте считается до вычета бонусов, поэтому capture при
сборке всегда не превышает холд.

### POST /orders/{id}/pay: повторный холд по заказу

Auth: `auth:sanctum`, доступ только владельцу заказа. Throttle: 5 запросов в минуту.

**Запрос:** пустой body.

**Ответ (200):**
```json
{
  "confirmationUrl": "https://yoomoney.ru/checkout/..."
}
```

`confirmationUrl` может быть null: холд создан по сохранённой карте заказа без редиректа.

**Ошибка (422):**
```json
{
  "message": "Недостаточно средств на карте",
  "reason": "insufficient_funds"
}
```

`reason` (новое) может быть null. В `message` попадает: при синхронном отказе
банка текст по коду причины (`Недостаточно средств на карте` и т. п.), при ошибке
запроса к ЮKassa текст `description` из её ответа или `Ошибка создания платежа`,
при отсутствии текста `Не удалось создать платёж`.

**Поведение сервера:**
- создаётся новый холд на `total` заказа; если к заказу привязана карта, холд идёт по её `payment_method_id`;
- запрос в ЮKassa отправляется с ключом идемпотентности `hold-{orderId}`;
- тип оплаты заказа не проверяется, ручка доступна и для заказа с `paymentType: "cash"`;
- каждая попытка пишет транзакцию типа `hold` со статусом `pending` (успех) или `canceled` (отказ).

### POST /orders/{id}/refund: возврат

Auth: `auth:sanctum`, доступ только владельцу заказа. Throttle: 5 запросов в минуту.

**Запрос:**
```json
{
  "amount": 500.00
}
```

`amount`: обязательное, числовое, минимум `0.01`.

**Ответ (200):**
```json
{
  "success": true,
  "message": "Возврат создан"
}
```

**Ошибки (422):**

| Условие | message |
|---|---|
| `amount` больше остатка | `Максимальная сумма возврата: 638` (значение подставляется без фиксированных двух знаков) |
| По заказу нет успешного списания | `Нет успешного списания для возврата` |
| Все платежи уже возвращены | `Нет доступных платежей для возврата` |
| Ошибка ЮKassa | текст `description` из ответа ЮKassa или `Ошибка возврата` |
| `amount` не передан | `Укажите сумму возврата` (ошибка валидации) |
| `amount` меньше `0.01` | `Сумма возврата должна быть больше 0` (ошибка валидации) |

**Поведение сервера:**
- максимум к возврату = `capturedAmount − refundedAmount`;
- сумма распределяется по успешным capture-транзакциям (холд и досписания) в порядке их создания, поэтому возврат после досписания разносится на несколько платежей;
- транзакция возврата создаётся в статусе `pending`; `refundedAmount` в заказе растёт только после вебхука `refund.succeeded` от ЮKassa;
- чек возврата: при активном фискализаторе ЮKassa чек синхронизируется из ЮKassa, при АТОЛ сервер пробивает собственный чек возврата.

### POST /payment-cards/bind: привязать карту заранее

Auth: `auth:sanctum`. Отдельного throttle нет.

**Запрос:** пустой body.

**Ответ (200):**
```json
{
  "confirmationUrl": "https://yoomoney.ru/checkout/..."
}
```

`confirmationUrl` может быть null (сервер отдаёт значение из ответа ЮKassa как есть).

**Ошибка (422):**
```json
{
  "message": "Не удалось привязать карту"
}
```

В `message` попадает текст ошибки ЮKassa, если она его прислала.

**Поведение сервера:** создаётся холд на 1 ₽ с чеком «Привязка банковской карты» и
транзакция без привязки к заказу. После вебхука `payment.waiting_for_capture` сервер
сохраняет карту пользователю и снимает холд 1 ₽ (списания не происходит), транзакция
переводится в `canceled`. Карты дедуплицируются по паре «последние 4 цифры + тип
карты»: повторная привязка той же карты обновляет `payment_method_id` существующей
записи. Первая карта пользователя сохраняется с `isDefault: true`.

### GET /orders/{id}: детали заказа (платёжные поля)

```json
{
  "id": 148,
  "status": "pending",
  "isPaid": true,
  "paymentType": "card",
  "heldAmount": 1138.00,
  "capturedAmount": 1138.00,
  "refundedAmount": 500.00,
  "surchargeAmount": null,
  "paymentDeclineReason": null
}
```

| Поле | Тип | Описание |
|---|---|---|
| `isPaid` | bool | Признак оплаты заказа |
| `paymentType` | string | `cash` или `card` |
| `heldAmount` | float, может быть null | Сумма подтверждённого холда |
| `capturedAmount` | float, может быть null | Списанная сумма (холд плюс досписания) |
| `refundedAmount` | float, может быть null | Возвращённая сумма, растёт по вебхуку `refund.succeeded` |
| `surchargeAmount` | float, может быть null (новое) | Сумма неуспешной доплаты при завершении сборки, заказ ожидает доплату |
| `paymentDeclineReason` | string, может быть null (новое) | Машинный код причины последнего отказа холда (`insufficient_funds` и т. п.). Присутствует в ответах `GET /orders`, `GET /orders/{id}`, `GET /orders/active`, `POST /orders/{id}/cancel` |
| `paymentCard` | объект | Помечен `whenLoaded`; ни одна ручка заказов эту связь не подгружает, поэтому поле в ответе отсутствует. Данные карты доступны через `GET /payment-cards` |

## Статусы оплаты

| Состояние | isPaid | heldAmount | capturedAmount | refundedAmount |
|-----------|--------|------------|----------------|----------------|
| Ожидает оплаты | false | null | null | null |
| Холд подтверждён | false | 1138.00 | null | null |
| Списано | true | 1138.00 | 1138.00 | null |
| Списано с досписанием | true | 741.00 | 900.00 | null |
| Частичный возврат | true | 1138.00 | 1138.00 | 500.00 |

`capturedAmount` превышает `heldAmount`, когда фактическая сумма сборки больше
холда и разница списана отдельным платежом по сохранённой карте.

## Серверная логика

### Списание при завершении сборки

Есть два режима, взаимоисключающих по фича-флагу `collector_payment`.

**Событийный режим (флаг выключен).** Сервер списывает деньги по событию перехода
заказа в статус `assembled` из курьерки. Условия: `paymentType: "card"`,
`heldAmount > 0`, `capturedAmount` пустой.
- `grand_total <= холда`: capture на фактическую сумму, остаток холда разблокируется;
- `grand_total > холда`: сначала досписание разницы по сохранённой карте, затем capture холда. Неуспешное досписание не отменяет capture холда: публикуется событие `order_payment_failed`, `isPaid` не меняется.

**Синхронный режим (флаг `collector_payment` включён).** Событийный capture отключён,
списание выполняет сборщик через внутреннюю ручку `POST /v1/internal/orders/{order}/settle-payment`.
Порядок операций: сначала доплата разницы, затем capture холда.
- Доплата не прошла: заказ помечается `surchargeAmount` и сроком ожидания, публикуется событие `order_surcharge_required`, клиенту уходит пуш. Холд остаётся нетронутым;
- Доплата прошла, capture упал: `surchargeAmount` не выставляется, ставится только страховочный срок, повторный вызов безопасен и доплату не дублирует;
- Срок ожидания доплаты задаётся настройкой `surcharge_wait_hours` (по умолчанию 24 часа). По истечении срока плановая команда `orders:cancel-expired-surcharge` (запуск каждую минуту) отменяет заказ в статусе `assembling`, возвращает доплату и снимает холд.

### Отмена заказа

При отмене заказа с `paymentType: "card"` сервер возвращает невозвращённый остаток
списанной суммы и снимает холд, если тот ещё не закрыт capture. Правило действует
для клиентской отмены (`POST /orders/{id}/cancel`), внешней отмены из курьерки и
автоотмены заказа самовывоза.

### Оплата наличными

Холд и capture не выполняются. При доставке заказа (`delivered`) с активной
интеграцией `fiscal` и положительной суммой `grand_total` из события доставки
сервер помечает заказ оплаченным и пробивает чек на эту сумму. Без активной
фискальной интеграции ни `isPaid`, ни чек не меняются.

### Частичный возврат при доставке

Если карточный заказ доставлен на сумму меньше списанной (курьер вернул часть
позиций), сервер автоматически возвращает разницу между `capturedAmount` и
фактически доставленной суммой.

## Фискальные чеки (54-ФЗ)

Активный фискализатор выбирается интеграцией `fiscal` (`driver`: `atol` или `yookassa`).

| Драйвер | Чек прихода по карте | Чек наличных | Чек возврата | `receiptUrl` |
|---|---|---|---|---|
| `yookassa` | формируется внутри платежа ЮKassa, статус синхронизируется из ЮKassa | независимый чек через ЮKassa | синхронизируется из ЮKassa | null |
| `atol` | отдельный чек в АТОЛ после успешного capture | чек в АТОЛ при доставке | отдельный чек в АТОЛ на каждый возврат | ссылка на чек в ОФД |

При активном АТОЛ объект `receipt` в запросы ЮKassa не передаётся, чтобы не пробить
чек дважды. Признак `send_receipt` (галочка в настройках интеграции `payment`,
по умолчанию `true`) управляет отправкой чека в ЮKassa.

Когда чек переходит в статус `succeeded`, сервер один раз отправляет пуш
`receipt_ready` (см. контракт чеков в `docs/specs/2026-07-09-fiscal-receipts-mobile-api-contract.md`).

## Вебхуки и внутренние ручки (server-to-server)

Ручки этого раздела вызываются платёжной системой, фискализатором и соседними
модулями. Мобильный клиент их не вызывает.

### POST /v1/webhooks/yookassa

Без авторизации, доступ ограничен списком IP-адресов ЮKassa (в окружениях `local`
и `testing` проверка отключена). Неизвестный IP: `403`.

| Событие | Действие сервера |
|---|---|
| `payment.waiting_for_capture` | холд подтверждён: проставляется `heldAmount`, сохраняется карта; для привязки карты холд 1 ₽ снимается |
| `payment.succeeded` | платёж списан: пишется capture-транзакция, `isPaid: true`, синхронизируется чек |
| `payment.canceled` | холд отменён: сохраняется код причины (`decline_reason`), публикуется `order_payment_failed` |
| `refund.succeeded` | увеличивается `refundedAmount`, публикуется `order_refunded`, пробивается или синхронизируется чек возврата |
| другое | записывается в лог, состояние не меняется |

Ответ всегда `200 {"status": "ok"}`.

### POST /v1/webhooks/atol

Без авторизации. Принимает `uuid`, `status` (`done` или `fail`) и `payload`
(`fn_number`, `fiscal_document_number`, `fiscal_document_attribute`,
`ofd_receipt_url`, `receipt_datetime`). При `done` чек переводится в `succeeded`
и отправляется пуш «Чек готов», при `fail` в `canceled`. Повторный колбэк по уже
пробитому чеку игнорируется. Ответ всегда `200 {"status": "ok"}`.

### POST /v1/internal/orders/{order}/settle-payment

Заголовок `X-Internal-Token` обязателен, сверка со значением `INTERNAL_API_TOKEN`.
Пустой сконфигурированный токен закрывает ручку. Несовпадение: `403`.

Запрос: `{"amount": 1234.56}` (обязательное, числовое, минимум 0).

| HTTP | Тело | Условие |
|---|---|---|
| `200` | `{"status": "ok", "payment_status": "paid"}` | Списание прошло или уже было выполнено ранее |
| `402` | `{"status": "failed", "message": "...", "surcharge_amount": 120.00}` | Доплата отклонена, заказ ожидает доплату |
| `503` | `{"status": "retry", "message": "Техническая ошибка списания, попробуйте ещё раз"}` | Доплата прошла или не требовалась, capture холда не удался; повторный вызов безопасен |

Для заказа с `paymentType: "cash"` ручка отвечает `200` без обращения в ЮKassa.

### POST /v1/webhooks/yandex-delivery и POST /v1/internal/yandex-claims/{claimId}/cancel

Ручки Яндекс Доставки без авторизации. Вебхук принимает `claim_id`, `status`,
`updated_ts`, `performer_info`, `tracking_url`, сверяет статус прямым запросом в
Яндекс и отвечает `200 {"status": "ok"}` в любом случае, включая неизвестную заявку.
Ручка отмены отвечает `200 {"status": "ok", "claim_status": "..."}`, при ошибке
отмены `500 {"status": "error", "message": "...", "claim_status": "..."}`,
при неизвестной заявке `404`.

## Возврат после оплаты на странице ЮKassa

Адрес возврата берётся из переменной окружения `YOOKASSA_RETURN_URL` (значение по
умолчанию `/`). В `.env` и `.env.example` текущего стенда указан адрес форка Aladdin
`https://store.aladdin.comrades.dev/payment/success`, под mendev значение не обновлено.

Результат оплаты отражается в полях заказа: подтверждённый холд заполняет
`heldAmount`, списание переводит `isPaid` в `true`, отказ холда заполняет
`paymentDeclineReason`.

---

## Требования на стороне ЮKassa

Сервер всегда передаёт `save_payment_method: true` при создании холда и берёт
идентификатор способа оплаты из ответа ЮKassa. Сохранение карт, повторные списания
по сохранённой карте, досписание и привязка карты работают, только когда магазину
в ЮKassa подключены автоплатежи. Факт подключения из кода storefront не
устанавливается, признак приходит из настроек интеграции.
