# Приложение курьера: вкладки «К доставке» / «В пути» и синхронизация совместной доставки

MID-273, MID-268 (re-test). Модуль `courier_assignment` включён на dev.
Все запросы: GraphQL `/graphql-delivery`, авторизация Sanctum Bearer-токеном.

## 1. Почему заказ виден в обеих вкладках (MID-273)

Сейчас приложение строит вкладки из двух разных запросов:

| Вкладка | Источник | Что отдаёт бэкенд |
|---|---|---|
| «К доставке» | `delivery_orders_paginate` | маршрут курьера целиком: ВСЕ его назначения независимо от статуса (1 ожидает, 2 в пути, 3 приехал, 4 доставлен) |
| «В пути» | `orders_paginate` | при включённом `courier_assignment` это список «назначенные мне» (контракт 2026-07-17, п.1): заказ попадает туда сразу после назначения сборщиком, ещё до «Поехали», и остаётся до конца дня |

Ни один из запросов не фильтрует по этапу доставки, поэтому назначенный заказ одновременно и в «К доставке» (карточка маршрута: статус, приоритет, «Поехали»), и в «В пути» (карточка заказа с таймером). После «Поехали» он тоже остаётся в обоих.

Дополнительно: карточка маршрута показывает `order.id`, карточка заказа показывает `order.number`. На видео это один заказ: «№ 65» (id) и «№ 61» (number). Показывать везде `number` (он же виден клиенту), см. MID-264.

## 2. Как строить вкладки

Обе вкладки берутся из ОДНОГО запроса `delivery_orders_paginate` и делятся по `status_id` назначения:

| `status_id` | Значение | Вкладка |
|---|---|---|
| 1 | Ожидает начала доставки | «К доставке» |
| 2 | В пути | «В пути» |
| 3 | Приехал на место выдачи | «В пути» (с отметкой «Приехал») |
| 4 | Доставлен | «Доставлено» |
| 5 | Отменён | не показывать |

Пример:

```graphql
query {
  delivery_orders_paginate(first: 50) {
    data {
      id
      priority
      status_id
      order {
        id
        number
        label
        status_id
        slot_start_date
        slot_end_date
        is_heavy
        couriers_count
        products_count
        client_info { name phone address entrance intercom floor flat }
      }
    }
  }
}
```

### Вкладка «Доставлено» и фильтр по статусу (MID-322, 2026-10-05)

До MID-322 доставленные назначения исчезали из `delivery_orders_paginate`, `delivery_orders` и `delivery_orders_item` после доставки последнего заказа рейса (рейс закрывался, а с ним скрывались все его назначения). Теперь доставленные (`status_id = 4`) заказы закрытых рейсов, вся история курьера, отдаются по явному фильтру `status_id`, содержащему 4, и в `delivery_orders_item`.

Порядок выдачи: сначала маршрут (1, 2, 3 по приоритетности и слоту), затем доставленные от свежих к старым.

У `delivery_orders_paginate` и `delivery_orders` появился необязательный аргумент `status_id: [Int!]`. История растёт, поэтому вкладку «Доставлено» лучше грузить отдельным запросом со своей пагинацией, а маршрут фильтром `[1, 2, 3]`:

```graphql
query {
  route: delivery_orders_paginate(first: 50, status_id: [1, 2, 3]) { data { id priority status_id order { id number } } }
  delivered: delivery_orders_paginate(first: 20, page: 1, status_id: [4]) {
    data { id status_id order { id number } }
    paginatorInfo { currentPage lastPage total }
  }
}
```

Без аргумента поведение прежнее: только текущий рейс (включая уже доставленные в нём заказы), история закрытых рейсов не отдаётся. Текущие сборки приложения строят вкладку «В пути» из `delivery_orders` без аргументов; в первой версии MID-322 история отдавалась и без фильтра, и у курьера в «В пути» оказались все 228 доставленных заказов (прод 07.10).

`orders_paginate` для вкладок курьера не использовать: при `courier_assignment` он нужен только как «назначенные мне» (справочный список), а не как этап доставки.

Кнопка «Поехали» (`DeliveryStart`) стартует первое назначение со `status_id = 1` по `priority`. Приоритет выставляется через `DeliveryOrderChangePriority`; у назначений, созданных сборщиком/админом, `priority` может быть `null`.

## 3. Совместная доставка: что меняется на бэкенде (MID-268, re-test)

Тяжёлый заказ везут два и более курьеров, поэтому этапы у них общие. Бэкенд теперь сам двигает назначения соисполнителей:

| Событие у курьера A | Что происходит у соисполнителя B |
|---|---|
| «Поехали» по тяжёлому заказу (`DeliveryStart`) | назначение B по этому заказу: 1 → 2 («В пути»), push `delivery_started` |
| очередь дошла до тяжёлого заказа после доставки/отмены предыдущего (`DeliveryFinish`, `OrderCancelByCourier`) | то же самое: 1 → 2, push `delivery_started` |
| «Приехал на место» (`DeliveryArrived`) | назначение B: 2 → 3 («Приехал»), push `delivery_arrived` |
| «Доставлено» (`DeliveryFinish`) | назначение B закрывается: → 4, push `order_closed_by_system` (без изменений) |

Исключение: если B прямо сейчас везёт ДРУГОЙ заказ (у него есть назначение в статусе 2 или 3 по другому заказу), его назначение по тяжёлому заказу не трогаем. Оно стартует само, когда очередь B дойдёт до него. Порядок `priority` и «приоритет не выбран» на синхронизацию больше не влияют.

Приложению по push `delivery_started` / `delivery_arrived` (поле `data.type`, `data.order_id` = внутренний id заказа) нужно перечитать `delivery_orders_paginate`: статус назначения изменился без действия пользователя.

## Push-уведомления (data.type)

| type | Кому | Когда |
|---|---|---|
| `delivery_started` | соисполнителям | их назначение переведено в «В пути» системно |
| `delivery_arrived` | соисполнителям | их назначение переведено в «Приехал» системно (новое) |
| `order_closed_by_system` | соисполнителям | заказ завершён/отменён другим курьером (без изменений) |
