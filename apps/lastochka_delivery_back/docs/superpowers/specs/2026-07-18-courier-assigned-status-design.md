# Статус «Назначен курьер» в АП (модуль courier_assignment) — дизайн

Дата: 2026-07-18. Задача: АП → Заказы → добавить статус «Назначен курьер» для системы, где в конце сборки сборщик сам назначает курьера. Работает ТОЛЬКО при включённом фича-флаге `courier_assignment` («Назначение курьера сборщиком»).

Базовая спека модуля: `2026-07-17-courier-assignment-design.md`.

## Проблема

Сейчас назначение курьера (`DeliveryAssignCouriers` сборщиком или REST `OrderController::delivery` из АП) автостартует рейс: заказ мгновенно становится «В доставке (4)», хотя курьер физически ещё не выехал. Состояние «Собран (3) + назначение» существует только для хвоста активного рейса. Админ в АП не видит, каким заказам курьер уже назначен.

## Решение (утверждено): полноценная ступень + виртуальный статус

### Семантика

«Назначен курьер» = `status_id = 3 (ASSEMBLED)` И существует активное назначение (`delivery_orders.order_id IN selfAndChildOrderIds` — та же логика, что резолвер колонки «Курьер» `OrderCouriersResolver`). Нового status_id в БД НЕТ: RabbitMQ-события, storefront, RetailCRM, консьюмеры не затрагиваются (для них заказ остаётся `assembled`).

Жизненный цикл при флаге ON: Собран → (сборщик/админ назначает курьера) → **Назначен курьер** → (курьер жмёт «Начать доставку», существующая мутация `DeliveryStart`) → В доставке → Доставлен.

### delivery_back

1. `DeliveryAssignCouriers::__invoke`: при `Order::isCourierAssignmentModuleEnabled()` — НЕ вызывать `DeliveryStart::deliveryStart` в ветке свободного рейса; `delivery_order` остаётся `WAIT_TO_START`, заказ остаётся 3. Ветка «рейс в пути → хвост с priority+1» сохраняется без изменений. При флаге OFF (чистый heavy-флоу) — автостарт байт-в-байт как сейчас.
2. REST `OrderController::delivery` (назначение/переназначение из АП): тот же гейт по флагу. Иначе назначение админом давало бы «В доставке», сборщиком — «Назначен курьер» (рассинхрон семантики).
3. Пуш курьеру «Вам назначен заказ» сохраняется в обоих путях. Видимость назначенного заказа у курьера уже обеспечена (`scopeByCourierAssignment` отдаёт `WAIT_TO_START`).
4. `DeliveryStart` — без изменений (переводит все `WAIT_TO_START` заказы рейса в 4).
5. Контракт мобилке `docs/specs/2026-07-17-courier-assignment-api-contract.md` — аддендум: при `courier_assignment_enabled` назначение НЕ запускает доставку; курьер обязан нажать «Начать доставку» (`DeliveryStart`); до этого заказ для клиента/АП остаётся собранным/назначенным.

### purchase_back

6. `Order::isCourierAssignmentModuleEnabled(): bool` — public static в модели (чтение `admin_settings.project_modules['courier_assignment']['enabled'] ?? false`, зеркало delivery_back). `OrderCourierAddValidator` переводится на хелпер (убирается приватный дубль).
7. `OrderFilter`: виртуальный код `FILTER_COURIER_ASSIGNED = 8`:

| Выбрано | Флаг courier_assignment | Условие |
|---|---|---|
| `[8]` | любой | `status_id=3 AND EXISTS назначение` |
| `[3]` | ON | `status_id=3 AND NOT EXISTS назначение` |
| `[3]` | OFF | `status_id=3` (текущее поведение, регрессии нет) |
| `[3,8]` | любой | `status_id=3` |

   EXISTS: `delivery_orders`, у которых `order_id` = сам заказ ИЛИ его подзаказ (`orders.parent_order_id = orders.id`). Композиция с виртуальным кодом 7 («Выдан») — в той же OR-группе `statuses()`.
8. Докстрока аргумента `statuses` в `OrderQueries.graphql` дополняется кодом 8.

### admin_front

9. Таблица `orders/index.vue`: для `status_id === 3` бейдж «Назначен курьер» вместо «Собрано» при включённом модуле (`moduleStore.isModuleEnabled("courier_assignment")`) и непустом `row.couriers`.
10. Фильтр `OrdersPageFilters.vue`: опция `{ id: 8, title: "Назначен курьер" }` между «Собрано» и «В доставке», видимая только при включённом модуле (список опций становится computed).
11. Карточка заказа `OrderPageAside.vue`: подпись шага 3 в статус-цепочке условная — «Назначен курьер» при включённом модуле и непустых `couriers` заказа (прецедент — условный «Выдан»/«Доставлен» на шаге 5).

## Fail-safe

Флаг OFF → автостарт и фильтр работают как сегодня, опция 8 не показывается, бейджи не меняются. Ошибки чтения флага (`?? false`) ведут к выключенной ветке.

## Краевые случаи

- Heavy-заказ, 2+ курьеров при флаге ON: оба назначения без автостарта, каждый курьер стартует свой рейс сам.
- Хвост активного рейса: заказ «Назначен курьер» до завершения текущего рейса и старта следующего — как и раньше, только теперь виден в АП отдельным статусом.
- Самовывоз: не назначается (существующая валидация), статус недостижим.
- Заказ 3 без назначения при флаге ON: «Собрано» в таблице и фильтре `[3]` — сигнал админу, что сборщик не назначил курьера.
- Фильтр `[8]` при флаге OFF (ручной URL): отработает по EXISTS-семантике, в UI опции нет — безвредно.

## Тесты

delivery_back (`tests/Feature`, DatabaseTransactions, паттерны DeliveryAssignCouriersTest):
1. Флаг ON: `DeliveryAssignCouriers` на обычный заказ → 200, `delivery_order WAIT_TO_START`, рейс НЕ стартовал (`started_at IS NULL`), заказ остаётся 3.
2. Флаг ON: REST `/backend-delivery/order/delivery` → то же.
3. Флаг OFF + heavy ON: назначение автостартует рейс, заказ 4 (регрессия).
4. Флаг ON: после назначения `DeliveryStart` курьером → рейс стартовал, заказ 4.

purchase_back (паттерн OrderIssuedStatusFilterTest):
5. `[8]` → только заказы 3 с назначением.
6. `[3]` при флаге ON → только заказы 3 без назначения.
7. `[3]` при флаге OFF → все заказы 3 (регрессия).
8. `[3,8]` → все заказы 3.
9. Композиция `[8,7]`/`[8,1]` — OR-группа не ломается.

admin_front — тестовой инфраструктуры нет; ручная E2E.

## Вне scope

Мобильное приложение (контракт передаётся аддендумом), синк на форки (по явной команде), подзаказы в `open.vue::orderStatusLabel`, реальный status_id в БД.

Ветки `feature/courier-assigned-status` в mendev_delivery_back, mendev_purchase_back, mendev_admin_front. Merge `--no-ff` + push + CI + E2E на dev — по явной команде. E2E: включить флаг, назначить курьера сборщиком (или REST), убедиться что заказ «Назначен курьер» в таблице/фильтре/карточке, стартовать доставку курьером → «В доставке».
