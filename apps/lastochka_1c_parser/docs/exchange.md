# Архитектура обмена

Данный документ описывает архитектуру и принципы обмена данными между ключевыми системами проекта: **RetailCRM**, **Bagisto**, **DeliverySystem** и брокером сообщений **RabbitMQ**.

Основная цель интеграции — обеспечить **надёжную, двустороннюю и независимую синхронизацию** данных между всеми участниками экосистемы без прямых связей между ними.  
Каждая система взаимодействует только с RabbitMQ.

Дополнительно в документе описана API интеграция между **Bagisto** и **DeliverySystem**. Данная интеграция не влияет на обмен данными, а предоставляет дополнительный функционал работы слотов доставки

## Элементы системы

- RetailCRM - CRM система
- Bagisto - интернет магазин
- DeliverySystem - система доставки
- RabbitMQ - брокер сообщений
- RetailBridge - сервис-прослойка между RetailCRM - RabbitMQ

## Состав обмена

- Товары
- Категории
- Заказы
- Клиенты
- Сотрудники
- Магазины

## API получения доступных слотов курьерской доставки.

Клиентская часть отправляет запрос с содержанием следующих полей

| Техническое название | Логическое название | Тип | Обязательное |
| --- | --- | --- | --- |
| latitude | Широта | Дробное число | Да  |
| longitude | Долгота | Дробное число | Да  |
| date | Дата доставки | Дата в формате Y-m-d (например 2022-12-30) | Да  |

**Бэкенд** клиентской части собирает корзину товара и внешние идентификаторы для системы доставки и отправляет запрос в **АПИ** системы доставки. Система доставки по полученным координатам производит поиск, находятся ли координаты в какой-либо зоне, если да то собирает доступные **слоты** на 7 дней, начиная от отправленного дня

Формат ответа

```json
{
  "slots" : [
    {
      "start" :"2025-11-07 16:00:00", // начало слота
      "end" : "2025-11-07 17:00:00" // конец слота
    },
    {
      "start" :"2025-11-07 17:00:00",
      "end" : "2025-11-07 18:00:00"
    },
    {
      "start" : "2025-11-07 18:00:00",
      "end" : "2025-11-07 19:00:00"
    }
  ],
  "min_order_price" : 500, // минимальная сумма заказа, если null то нет ограничений
  "shipping_free_from" : 1500, // после какой суммы бесплатная доставка, если null то нет бесплатной доставки
  "shipping_price" : 200 // стоимость доставки
}
```

## Регистрация событий в RMQ

Любой узел системы при следующих событиях отправляет данные в RMQ

### **1\. Товары (**`product.*`**)**

| Событие | Когда отправлять |
| --- | --- |
| `product.created` | Когда создан новый товар в системе (впервые добавлен в каталог) |
| `product.updated` | При изменении цены, остатков, описания, фото, SEO, SKU и т.п. |
| `product.deleted` | Когда товар удалён или деактивирован: реквизит `DelProd=true` в выгрузке либо товар не попал в полную выгрузку при включённом чекбоксе «Удалять товары, не попавшие в полную выгрузку 1С» (команда `deactivate` от 1С, см. `1c-setup-guide.md`) |
| `product.stock.changed` | При изменении остатков в магазине (1С, RetailCRM, сайт) |

#### Цены от количества (`price_tiers`, MID-308)

Ключ `price_tiers` едет в `product.price_updated` и в полном событии товара (`product.created`, `product.updated`):

```json
"price_tiers": [
  { "min_quantity": 2, "price": 249 },
  { "min_quantity": 5, "price": 199 }
]
```

- `min_quantity` и `price` в тех же единицах, что поле `price` события (шт, кг, л): порог и цена за базовую единицу товара. Цена ступени действует на все единицы позиции.
- Семантика на приёме. Ключа нет: ступени магазина не трогаются. `[]` или `null`: лесенка магазина удаляется. Массив: полная замена лесенки.
- Ключ кладётся, когда у товара есть ступени розничного типа цены (тот же тип, из которого берётся `price`, см. `ONEC_RETAIL_PRICE_TYPES`), а также один раз со значением `[]`, когда лесенка розничного типа стала пустой (реквизит `<ЦеныОтКоличества>` пропал у товара, у которого ступени были). У остальных товаров состав событий прежний.
- `product.price_updated` публикуется и тогда, когда цена не изменилась, а изменилась только лесенка (в том числе при её очистке до `[]`, см. пункт выше).
- Команда `php artisan 1c:resync-prices` переиздаёт розничную цену вместе с сохранённой лесенкой.
- Формат реквизита в выгрузке 1С: `commerceml-format.md`, раздел «Цены от количества».

## RetailBridge - сервис-прослойка

**RetailBridge** - это сервис-прослойка, который обеспечивает двусторонний обмен данными между **RabbitMQ** и **RetailCRM**.  
Он выступает посредником между событийной шиной и CRM, синхронизируя заказы, клиентов, статусы и другие сущности.

---

### Основные функции

- **Приём событий из RabbitMQ**  
    Обрабатывает сообщения из очередей и конвертирует их в REST-запросы к RetailCRM API.
- **Отправка событий в RabbitMQ**  
    Принимает вебхуки и уведомления из RetailCRM (создание/изменение заказов, клиентов, статусов) и публикует соответствующие события обратно в RabbitMQ.
- **Хранение маппингов**  
    Ведёт соответствие ID между RetailCRM и другими системами (например, ID клиента в CRM ↔ ID во внешней системе)

### Обмен магазинами (shops)

**Направление:** RabbitMQ → RetailCRM

Магазины из внешних систем (Bagisto, DeliverySystem) синхронизируются с RetailCRM как **sites**.

**Особенности:**
- Sites в RetailCRM — справочник с ограниченным набором полей
- Endpoint `POST /api/v5/reference/sites/edit` работает как **upsert**
- Sites не имеют numeric ID, используется `code`
- **Удаление sites не поддерживается** RetailCRM — событие `shop.deleted` только логируется
- Расширенные поля (schedule, coordinates, slot_time) хранятся в `event_sync_metadata.data`

**Маппинг полей:**

| Exchange | RetailCRM | Примечание |
|----------|-----------|------------|
| `shop_code` | `code` | Уникальный код сайта (max 50 chars, [a-zA-Z0-9_-]) |
| `title` | `name` | Название, fallback на shop_code |
| `url` | `url` | URL сайта |
| `country_iso` | `countryIso` | Код страны (default: KZ) |

**Запуск consumer:**
```bash
php artisan rabbitmq:consume shop
```
