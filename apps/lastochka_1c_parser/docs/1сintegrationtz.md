# ТЗ: Настройка и мониторинг обмена с 1С из админки

**Версия:** 2.0
**Дата:** 2026-03-26

---

## 1. Цель

Админ курьерки видит в настройках карточку "1С:Торговое предприятие", где может:
1. Задать логин/пароль Basic Auth (которым 1С авторизуется на парсере)
2. Увидеть URL endpoint-а обмена, чтобы передать его менеджеру для настройки в 1С
3. Видеть **статус последнего обмена**: когда 1С последний раз стучалась, была ли попытка успешной
4. Видеть **диагностику данных**: пришли ли товары, цены, остатки, заказы — и что из реквизитов отсутствует

**Результат:** менеджер настраивает 1С самостоятельно (видит URL и credentials), а админ видит — работает ли обмен и что именно не так, без SSH на сервер.

---

## 2. Контекст

### Где живёт

| Слой | Модуль | Что делает |
|---|---|---|
| **Backend (master)** | `aladdin_docker/aladdin_admin_back` | Дескриптор `OneCIntegrationDescriptor`, сохранение credentials, отображение URL |
| **Backend (slave)** | `alladin_1c_parser` | Потребление credentials через RabbitMQ, фиксация результатов обмена, публикация диагностики |
| **Frontend** | `aladdin_admin_front` | Карточка 1С в настройках интеграций (credentials + URL + статус + диагностика) |

### Триггеры

- **Настройка credentials:** админ заполняет логин/пароль → сохранение → RabbitMQ → парсер применяет
- **Фиксация обмена:** 1С стучится на `/1c-exchange` → парсер обрабатывает → записывает результат в `exchange_logs` → публикует событие диагностики в RabbitMQ
- **Отображение статуса:** UI запрашивает текущий статус обмена через GraphQL

### Связь с системой

**Существующая инфраструктура:**
- `IntegrationConfig` модель/GraphQL/RabbitMQ entity (реализовано для SMS)
- `IntegrationConfigModal.vue` (динамический, генерирует поля по schema)
- `exchange_logs` таблица в БД парсера (уже фиксирует все обмены)

**Новое:**
- Дескриптор `OneCIntegrationDescriptor` (admin_back) — credentials + read-only URL
- Событие `integration_config.1c_status` — парсер публикует результат обмена
- Блок диагностики в UI карточки 1С

## 3. Данные

### 3.1 Credentials (настраиваемые)

Только логин/пароль для Basic Auth. Остальные параметры импорта — пока через `.env`.

```
IntegrationType:
  type: "1c"
  label: "1С:Торговое предприятие"
  drivers:
    - name: "commerceml"
      label: "CommerceML 2.x"
      credentials_schema:
        - field: "login",    label: "Логин обмена",  type: "text",     required: true, placeholder: "1c_exchange"
        - field: "password", label: "Пароль обмена", type: "password", required: true
```

### 3.2 URL endpoint-а (read-only, не хранится в credentials)

Отображается в UI как информационное поле (не редактируемое):

```
URL обмена: https://1c.alladin.comrades.dev/1c-exchange
```

Значение берётся из env `ONEC_EXCHANGE_URL` на стороне admin_back (или формируется из домена парсера).

### 3.3 Архитектура обмена: узлы и типы данных

**Важно:** В 1С может быть несколько узлов обмена, которые стучатся на один и тот же URL `/1c-exchange`. Например:
- Узел 1: выгружает товары (каталог + цены/остатки)
- Узел 2: обменивается заказами

При этом один узел в рамках одного сеанса может передать и каталог (`type=catalog`), и заказы (`type=sale`). Парсер не знает и не должен знать, сколько узлов настроено — он просто обрабатывает каждый входящий запрос и фиксирует результат **по типу данных**.

**Типы данных (фиксируются раздельно):**

| Тип | Файлы | Направление | Что фиксировать |
|---|---|---|---|
| `catalog` | `import.xml` | 1С → парсер | Категории, товары, пропущенные реквизиты |
| `offers` | `offers.xml`, `prices___*.xml` | 1С → парсер | Цены, остатки, товары без цены/остатка |
| `rests` | `rests___*.xml` | 1С → парсер | Остатки |
| `orders_import` | `orders___*.xml` | 1С → парсер | Статусы заказов от 1С |
| `orders_export` | XML ответ на `mode=query` | парсер → 1С | Заказы, отданные в 1С, позиции без external_id |

### 3.4 Статус обмена (из парсера)

Парсер фиксирует результат **каждой операции по типу данных**. Admin_back хранит последний статус по каждому типу для отображения в UI.

**Агрегированная структура для UI:**

```json
{
  "last_connection_at": "2026-03-26T10:30:00Z",
  "catalog": {
    "last_at": "2026-03-26T06:00:00Z",
    "success": true,
    "categories_count": 45,
    "products_count": 1230,
    "warnings": ["3 товара без артикула", "15 товаров без штрихкода"]
  },
  "offers": {
    "last_at": "2026-03-26T10:15:00Z",
    "success": true,
    "prices_count": 1230,
    "stocks_count": 1225,
    "warnings": ["12 товаров без цены", "5 товаров без остатка"]
  },
  "rests": {
    "last_at": "2026-03-26T10:15:00Z",
    "success": true,
    "stocks_count": 1225,
    "warnings": []
  },
  "orders_import": {
    "last_at": "2026-03-26T10:20:00Z",
    "success": true,
    "processed_count": 5,
    "warnings": []
  },
  "orders_export": {
    "last_at": "2026-03-26T10:20:00Z",
    "success": true,
    "exported_count": 3,
    "pending_count": 0,
    "warnings": ["2 позиции без external_id"]
  }
}
```

Каждый тип обновляется **независимо**. Если в одном сеансе пришли и товары, и заказы — обновятся оба типа. Если из разных узлов — каждый обновит свой тип.

### 3.5 Устаревание данных (stale detection)

**Проблема:** 1С может перестать присылать определённые файлы (цены, остатки) — из-за изменения настроек узла, ошибки в 1С, удаления регламентного задания. Админ должен видеть, что данные устарели.

**Механизм:** для каждого типа данных, который **хотя бы раз** приходил, отслеживается время с последнего обмена. Если превышен порог — тип помечается как `stale`.

**Пороги устаревания (по умолчанию):**

| Тип | Порог | Обоснование |
|---|---|---|
| `catalog` | 48 часов | Каталог обычно выгружается раз в 4-24 часа |
| `offers` | 2 часа | Цены/остатки обычно каждые 15-60 минут |
| `rests` | 2 часа | Остатки — аналогично offers |
| `orders_import` | 2 часа | Статусы от 1С — регулярно |
| `orders_export` | 2 часа | 1С забирает заказы регулярно |

**Состояния типа данных в UI:**

| Состояние | Условие | Отображение |
|---|---|---|
| **Нет данных** | `last_at = null` (никогда не приходил) | Серый, "Не получено" |
| **Актуально** | `now - last_at < порог` | Зелёный ✅ |
| **Устарело** | `now - last_at >= порог` | Оранжевый ⏰ "Не обновлялось X часов" |
| **Ошибка** | `success = false` | Красный ❌ с текстом ошибки |

**Важно:** тип в состоянии "Нет данных" — это **не ошибка**. Возможно, 1С просто не настроена выгружать этот тип. Предупреждение показывается только если данные **были, а потом перестали** приходить (состояние "Устарело").

### 3.5 Событие диагностики (RabbitMQ, парсер → admin_back)

**Routing key:** `1c_exchange.status`

Парсер публикует **после каждой завершённой операции** — отдельно для каждого типа данных:

```json
{
  "event_id": "uuid",
  "event_timestamp": "2026-03-26T10:30:00Z",
  "event_source": "1c_parser",
  "data_type": "catalog",
  "success": true,
  "records_count": 1230,
  "error": null,
  "counters": {
    "categories_count": 45,
    "products_count": 1230
  },
  "warnings": [
    {"code": "missing_sku", "count": 3, "message": "3 товара без артикула"},
    {"code": "missing_barcode", "count": 15, "message": "15 товаров без штрихкода"}
  ]
}
```

**Примеры по типам:**

**`data_type: "offers"`:**
```json
{
  "counters": {"prices_count": 1230, "stocks_count": 1225},
  "warnings": [
    {"code": "missing_price", "count": 12, "message": "12 товаров без цены"},
    {"code": "missing_stock", "count": 5, "message": "5 товаров без остатка"}
  ]
}
```

**`data_type: "orders_export"`:**
```json
{
  "counters": {"exported_count": 3, "pending_count": 0},
  "warnings": [
    {"code": "missing_external_id", "count": 2, "message": "2 позиции без external_id"}
  ]
}
```

### 3.6 Маппинг credentials → env парсера

| Поле credentials | Текущий env | Назначение |
|---|---|---|
| `login` | `ONEC_EXCHANGE_LOGIN` | Basic Auth — 1С авторизуется этим логином на `/1c-exchange` |
| `password` | `ONEC_EXCHANGE_PASSWORD` | Basic Auth |

## 4. Логика

### 4.1 Happy path: первоначальная настройка

```
1. Админ → "Настройки" → "Интеграции" → карточка "1С:Торговое предприятие"
2. Видит:
   - URL обмена: https://1c.alladin.comrades.dev/1c-exchange (read-only, для копирования)
   - Логин обмена: [пусто]
   - Пароль обмена: [пусто]
   - Статус: "Обмен ещё не выполнялся"
3. Заполняет логин/пароль → "Сохранить"
4. Credentials → RabbitMQ → парсер (upsert в локальную integration_configs)
5. Админ передаёт менеджеру: URL + логин + пароль
6. Менеджер настраивает в 1С: Обмен данными → Узлы обмена → указывает URL и credentials
7. 1С выполняет первый обмен → стучится на /1c-exchange с этими credentials
8. Парсер обрабатывает, фиксирует результат в exchange_logs
9. Парсер публикует событие 1c_exchange.status → RabbitMQ → admin_back
10. Админ видит в карточке (статус по каждому типу данных раздельно):
    - Каталог: 26.03.2026 06:00 ✅ — 45 категорий, 1230 товаров
    - Цены/остатки: 26.03.2026 10:15 ✅ — 1230 цен, 1225 остатков
    - Заказы (импорт): ещё не было
    - Заказы (экспорт): ещё не было

Примечание: типы обновляются независимо — если 1С настроена
через 2 узла (один шлёт товары, другой заказы), каждый
обновит свой тип. Если один узел шлёт всё — обновятся все типы.
```

### 4.2 Happy path: диагностика проблем

```
1. Админ видит в карточке (каждый тип данных отдельно):
   - Каталог: 26.03.2026 10:30 ⚠️ — 1230 товаров (3 без артикула, 15 без штрихкода)
   - Цены/остатки: 26.03.2026 10:15 ⚠️ — 12 товаров без цены, 5 без остатка
   - Заказы (экспорт): 26.03.2026 10:20 ⚠️ — 2 позиции без external_id
   - Заказы (импорт): 26.03.2026 10:20 ✅ — 5 обработано
2. Админ понимает что делать: связаться с 1С-разработчиком
   для заполнения недостающих реквизитов
```

### 4.3 Happy path: данные перестали приходить

```
1. Цены приходили каждые 15 минут, но 3 часа назад перестали
2. Админ видит в карточке:
   - Каталог: 26.03.2026 06:00 ✅
   - Цены/остатки: 26.03.2026 07:15 ⏰ Не обновлялось 3 часа
   - Заказы: "Не получено" (серый — никогда не приходили, это нормально)
3. Админ понимает: проблема с выгрузкой цен из 1С,
   нужно проверить регламентное задание в 1С
```

### 4.3 Edge cases

| Случай | Поведение |
|---|---|
| **1С ни разу не стучалась** | Все типы данных: "Ещё не было". Диагностика пуста |
| **1С стучалась с неверным паролем** | Парсер вернул 401. Фиксируется: "Последняя попытка: неудачная авторизация" |
| **Credentials не настроены** | Парсер использует fallback из `.env`. UI показывает "Credentials не заданы через админку" |
| **Один узел шлёт товары, другой — заказы** | Каждый тип обновляется при своём обмене, независимо от узла. В UI видно время каждого типа отдельно |
| **Один узел шлёт и товары, и заказы** | В одном сеансе обновятся оба типа: `catalog` и `orders_import`/`orders_export` |
| **Каталог пришёл, но цены не пришли** | `catalog` ✅, `offers` — "Не получено" (серый). Не ошибка — возможно узел не настроен |
| **Цены приходили, но перестали** | `offers` показывает ⏰ "Не обновлялось X часов" (stale). Админ видит что данные устарели |
| **Остатки не пришли ни разу** | `rests` — "Не получено" (серый). Могут приходить в составе `offers` — тогда offers актуален |
| **1С отключили регламентное задание** | Все типы постепенно перейдут в stale. Последнее подключение тоже устареет |
| **Парсер недоступен для RabbitMQ** | Событие credentials остаётся в outbox. Статус не обновляется до восстановления |

### 4.4 Error handling

| Ошибка | Где | Действие |
|---|---|---|
| Невалидный XML от 1С | alladin_1c_parser | Зафиксировать в exchange_logs, опубликовать статус с error |
| 1С не авторизовалась | alladin_1c_parser | Зафиксировать failed auth attempt, опубликовать статус |
| RabbitMQ недоступен | publish-outbox | Outbox retry |
| Расшифровка credentials провалена | alladin_1c_parser | Fallback на .env, логировать critical |

| **Работает** | Все типы данных актуальны, нет критических проблем |
| **Есть замечания** | Обмен идёт, но есть пропущенные реквизиты (⚠️) |
| **Данные устарели** | Тип данных ранее приходил, но не обновлялся дольше порога (⏰) |
| **Не получено** | Тип данных ни разу не приходил (серый — это не ошибка, может быть не настроен в 1С) |
| **Ошибка** | Последний обмен данного типа завершился ошибкой (❌) |

## 7. Нефункциональные требования

### Безопасность
- Credentials шифруются в БД (`encrypted:json`)
- Password маскируется в GraphQL-ответе
- URL обмена — read-only, не хранится в credentials

### Обратная совместимость
- Если credentials не заданы через админку → парсер использует `.env` (`ONEC_EXCHANGE_LOGIN`, `ONEC_EXCHANGE_PASSWORD`)
- Диагностика не ломает текущий обмен — только читает из существующих `exchange_logs`
